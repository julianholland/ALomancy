Test tiers: every test carries `@pytest.mark.unit` or `@pytest.mark.integration` (`tests/conftest.py` fails collection otherwise, because `-m unit` silently skips an unmarked test). `slow` marks real training or anything over ~2 s even on tmpfs; it is left out locally and runs in CI. `tests/conftest.py` puts pytest's temp dir on `/dev/shm` when usable: `GlobalDatabase` construction is SQLite fsync-bound (3–6 s on a btrfs `/tmp`, 5 ms on tmpfs), which took the suite from 278 s to 18 s. `ALOMANCY_TEST_DISK_TMP=1` or `--basetemp` opts out. The pytest config lives only in `pyproject.toml`. CI runs the full suite on one Linux job for pull requests and the full OS/Python matrix on pushes and releases.

Pre-commit hooks run `ruff` (with `--fix`) and the fast test tier on every commit. Install with `pre-commit install`.

## Logging

Warnings and coded events also go to `results/events.jsonl` (next to the log file; `utils/logging_config.JsonlEventHandler`): every WARNING+ record, plus any record carrying `extra={"event": "<code>", "data": {...}}`, tagged with the current AL loop (`set_current_loop`, set by `iterate_loops`; a module global, not a ContextVar, because `RemoteJobExecutor` logs from worker threads). The loop report counts these instead of parsing log text: give a new warning an event code when the report should count it. Keep message text unchanged where `analysis/timing_plots` regex-parses it: the `@phase` decorator's "Phase %s started for %s." and `_mark_phase_done`'s "Phase %s marked complete for %s." (the phase boundaries, for every workflow), "Starting AL loop %d", "Training set size: %d", "Completed AL loop %d, ..." and "High-accuracy evaluation completed for %d structures.". `tests/analysis_tests/test_timing_plots.py` parses a log the real decorator wrote, so a renamed message fails a test.

All output goes through Python's `logging` module. No bare `print()` calls exist in `src/`.

```python
# Single configuration point — called in CommitteeUncertaintyWorkflow.__init__
from alomancy.utils.logging_config import setup_logging

setup_logging(verbose=1, log_file="results/my_run.log")
```

| `verbose` | Console | File (`results/alomancy.log`) |
|---|---|---|
| 0 (default) | WARNING+ only | DEBUG always |
| 1 | INFO (step progress) | DEBUG always |
| 2+ | DEBUG (per-job detail) | DEBUG always |

The file handler always writes DEBUG so every run produces a complete timestamped record. ExPyRe job stdout/stderr are captured at DEBUG level.

Each module declares `logger = logging.getLogger(__name__)` — no per-module setup needed. The `"expyre"` logger is also routed through the same handlers.

**Testing logs:** pytest's `caplog` does not intercept alomancy logs because `propagate=False` is set on the root alomancy logger. Attach a `logging.Handler` directly to `logging.getLogger("alomancy")` in tests that need to assert on log output (see `TestDisplayWorkflowSummary`'s `_capture` helper in `test_committee_uncertainty_workflow.py`).

## Architecture

ALomancy implements active learning (AL) workflows for training machine-learned interatomic potentials (MLIPs). The core loop is: **train MLIP committee → MD structure generation → uncertainty-based selection → DFT evaluation → extend training set → repeat**.

### Core layer (`src/alomancy/core/`)

`ActiveLearningWorkflow` (`active_learning_workflow.py`, abstract) owns everything generic to active learning; concrete workflows subclass it, declare their settings as class attributes (`NAME`, `KWARGS_KEY`, `KWARGS_DEFAULTS`, `NEW_STRUCTURE_CONFIG_TYPE`, optional `validate_settings()`) and implement only `run()`, which sets the order of the steps. Developer guide: `docs/writing_a_workflow.md`. Workflows are registered in `registry.py` under the `"al_workflow"` category (`workflow_class=...`), and `build_workflow(jobs_dict)` (defined in the parent, re-exported by `committee_uncertainty_workflow.py` for existing imports) dispatches on `general.al_workflow` (default `"committee_uncertainty"`). **The user-facing entry point is `ALomancy`** (`core/entry.py`, exported lazily from `alomancy/__init__.py` via module `__getattr__` — never import `core` eagerly there, it must run after the `.expyre` seeding/`Agg` setup): `ALomancy(path_or_dict)` loads a path with `load_dictionaries`, calls `build_workflow`, exposes `.workflow`/`.run()` and delegates other attributes to the workflow; `alomancy run config.yaml` is the CLI equivalent. Constructing a skeleton class directly with a config whose `general.al_workflow` names a different skeleton raises `ValueError` in `ActiveLearningWorkflow.__init__` — the config, not the imported class, picks the architecture. Modules (trainer/generator/evaluator/initialiser) are still resolved from config through the same registry, never by subclassing.

Parent helpers a `run()` calls: `prepare_run()` (curation-policy check, `pre_run_checks`, resume or `_initialize_training_set` cold/warm start, redundancy + split filters + curation; returns the first loop), `iterate_loops(start)` (yields `LoopContext(loop, base_name, workdir, train, test, train_only, plots_dir)`, writes `train_set.xyz`/`test_set.xyz`, skips `loop.done` loops), `train_models(ctx, seeds, *, min_successful=1)` → `list[TrainedModel]` (one model per seed on one shared train/valid/test split, **one parallel `submit_n` batch**, per-fit caching, seed recorded in `training/fit_i/fit_seed.json` with a warning — not a retrain — on mismatch, then `results/best_model/` update), `seeds(n)` (`general.seed + i`, unchanged mapping so cached fits stay valid), `best_model(models)` (`rank_committee`), `generate_candidates(ctx, model)`, `predict(ctx, models, structures)` (one parallel batch of `mlip/predict.predict_with_model`), `high_accuracy_evaluate(ctx, structures)` (sets `job_id`/`needs_relaxation` from `force_ceiling`, DFT, `clean_structures` with `NEW_STRUCTURE_CONFIG_TYPE` + `al_loop`), `add_to_dataset(ctx, structures)` (`test_ratio` split or `fixed_test` diagnostics), `finish_loop(ctx)`.

**`@phase(name, load=...)`** wraps loop steps with restart sentinels: if `results/<loop>/<name>.done` exists the step is skipped and `load(self, ctx, *args, **kwargs)` rebuilds its result from the files the step wrote (the decorator never stores return values itself); otherwise it runs and writes the sentinel after success. A phase name may run once per loop (`_phases_run`); a second call raises unless given `phase_name="..."`. All three loop steps are phases: `train_mlip` (parent's `_train_models_phase`, loader re-reads each `fit_i`), `generate_structures` (each child's selection step, e.g. `structure_generation/high_sd_structures.xyz`) and `high_accuracy_eval` (parent's `high_accuracy_evaluate`, loader re-reads `high_accuracy_eval_results.xyz` via the evaluator's `read_existing_result` and relabels via `_label_new_structures`); `loop.done` is written by `finish_loop`. The evaluator module also still checks/writes `high_accuracy_eval.done` itself (same file) because initialization calls it outside any loop. Sentinel and file names are unchanged from before the split so results directories written by older versions resume mid-loop — `tests/core_tests/test_committee_uncertainty_workflow.py::test_resumes_existing_mid_loop_results_without_redoing_work` guards this.

Children: `CommitteeUncertaintyWorkflow` (`committee_uncertainty_workflow.py`; `general.committee_uncertainty_kwargs.num_of_models_in_committee`, default and minimum 3, validated at construction; `select_uncertain` = best model → `generate_candidates` → `predict` with the whole committee, best first as `"base_mlip"` → `find_high_sd_structures`; `plot_loop` keeps the existing committee plots) and `RandomSelectionWorkflow` (`random_selection_workflow.py`; one model, `general.num_of_structures_per_loop` candidates chosen at random seeded by `general.seed + loop`, saved to `structure_generation/random_selection_structures.xyz`; config_type `random_selection`; a baseline comparator) and `NoveltySelectionWorkflow` (`novelty_selection_workflow.py`; one model; `select_novel` describes candidates with redundancy removal's `char_vec_128` (`utils/remove_redundancy.descriptors_for_atoms`, built like `_prepare_for_storage` so it matches the DB cache, never stored), stacks them after every non-`is_duplicate` DB descriptor (`_cached_descriptors`), and uses deduplicate_lib's `binary_search_tolerance` (via `PerturbedDatasetReclustering`, `perturbations_per_vector=1`) on `_CandidateDistanceMatrix` — a `DistanceMatrix` whose unique count covers candidate rows only — to find the largest tolerance leaving ≤ `general.num_of_structures_per_loop` candidates with no neighbour within it; DB rows go first because `DistanceMatrix` always marks row 0 unique; more than n (no exact tolerance) is trimmed by nearest-neighbour distance, fewer is accepted; saved to `structure_generation/novelty_selection_structures.xyz`; config_type `novelty_selection`). Generic split settings live in `general.dataset_kwargs` (`test_ratio`, `target_config_types` required; `valid_fraction`, `valid_config_types`, `grouped_splits`, `grouped_validation`, `fixed_test`), run control in `general` (`train_only`); their old locations under `committee_uncertainty_kwargs` are in `_MOVED_KEYS` and raise with the new path. **Anything submitted remotely stays a module-level function** (ExPyRe pickles by reference): never make a remote worker a method of a workflow class.

All results land under `results/<base_name>/` with a fixed subdirectory layout. The workflow has **idempotency logic** throughout: each step checks for existing output files and skips remote submission if they exist, enabling restart after failures.

`run()` calls `self.pre_run_checks()` first, which calls `display_workflow_summary()` (logs a per-phase settings summary — flattened from each phase's job dict up to 2 levels deep, so it reflects whatever module/calculator is configured without hardcoding per-algorithm keys — plus a table of HPC profiles in use: GPU/partitions/node stats/job types/installed alomancy version) and then checks the installed version (`alomancy.version.__version_tuple__`) against the latest published PyPI release: warns if behind by a minor release, raises `RuntimeError` if behind by a major release. Skipped gracefully on network failure (never blocks an offline HPC run) and skipped outright under `ALOMANCY_TEST_MODE`/`ALOMANCY_MOCK_EXTERNAL` (never makes a real network call in tests).

### Configuration (`src/alomancy/configs/`)

`load_dictionaries(config_path)` reads a YAML file into a `jobs_dict` passed to the workflow constructor. Four top-level keys are required: `initialization`, `mlip_committee`, `structure_generation`, `high_accuracy_evaluation`. Each carries a `name`, `max_time`, and `hpc` value.

**HPC string resolution**: `hpc:` may be either a dict (full inline profile, backwards-compatible) or a string name (e.g. `hpc: 'raven_gpu'`). When it is a string, `load_dictionaries` looks it up in `~/.alomancy/hpc_config.yaml` (loaded by `global_config._load_global_hpc_config()`) and substitutes the full dict in-place. Raises `ValueError` if the named profile is not found — message directs the user to `alomancy add-hpc`.

`global_config.py` holds path constants (`ALOMANCY_HPC_CONFIG = ~/.alomancy/hpc_config.yaml`, `EXPYRE_CONFIG = ~/.expyre/config.json`) and `_load_global_hpc_config()`.

`RemoteInfo` and `get_remote_info()` convert a job sub-dict into an Expyre `RemoteInfo` object. The `sys_name` field maps to an Expyre system name (defined in the user's Expyre config, not in this repo).

### Remote execution (`src/alomancy/remote_submission/executor.py`)

**See `docs/remote_submission_architecture.md` for the full picture**: a from-source audit of every function in `remote_submission/` (submitters, executor, `RemoteInfo`) plus a strategy review, covering exactly what's tested vs. not, dead code/config fields, and case studies tracing several real production incidents (a permanently-lost committee model, silent local-disk exhaustion, a corrupted-then-diagnosed parity-plot dataset) back to specific gaps — most of which are now fixed and cross-referenced there. Read it before making non-trivial changes to this subsystem; the summary below covers only what every session needs to know up front.

`RemoteJobExecutor` wraps Expyre's `ExPyRe`. Call pattern: `submit_multiple_jobs → run_all_jobs_bounded → cleanup_jobs`; the convenience method `run_and_wait` does all three steps. `run_all_jobs_bounded` runs a `ThreadPoolExecutor(max_workers=remote_info.max_num_of_concurrent_jobs)`, one `.start()`+`.get_results()` task per job — jobs beyond the cap queue automatically and the pool starts the next one the instant a worker thread frees up (success or failure), rather than submitting everything up front and waiting for results strictly in submission order. **ExPyRe's job DB is not thread-safe by default**: `expyre.config.db` is a single module-level sqlite3 connection opened with `check_same_thread=True`, and every read/write funnels through one choke point (`JobsDB._execute`). `_ensure_expyre_db_thread_safe()` (called once per `run_all_jobs_bounded`) reopens that connection with `check_same_thread=False` and wraps `_execute` in a lock — locking only the brief DB transaction, not the callers' polling sleeps, so real concurrency of the waiting is preserved. Submitters that mix job kinds in one pool (e.g. `ase_remote_submitter`'s GO/SP split, see below) pass a per-job `"function"` override in each `job_configs[i]` dict, which `submit_multiple_jobs` honours in place of its shared `function` argument.

**Transient remote failures are resumed, not treated as permanent** (`_get_results_with_resume`, called from `_run_single_job`): a `get_results()` exception is resumed on the *same* job object, rather than abandoning it, whenever `job.status` is in `_RESUMABLE_JOB_STATUSES` — the ongoing statuses (`created`/`submitted`/`started`, expyre raised from transport, e.g. an rsync "No space left on device", before ever updating status for that poll) **plus** `'succeeded'` (expyre sets this *before* it copies output files back to `cwd`, so a local ENOSPC-class failure during that copy-out alone still has status `'succeeded'` and is just as safe to retry — remote status is already `'done'`, so re-entering `get_results()` goes straight back to re-attempting the copy). Transport exceptions get up to 5 retries with exponential backoff; `ExPyReTimeoutError` gets exactly 1 — tracked with **separate counters per exception type**, not one shared counter, so an interleaved sequence of both types can't exhaust the wrong budget. Once `job.status` reaches `'failed'`/`'died'` (expyre's only two genuinely terminal statuses, both set *before* it raises), the exception re-raises immediately — no retry. A definitively died job (`ExPyReJobDiedError`) gets one fresh resubmission (`job.start(force_rerun=True)`, after `_salvage_partial_output` runs on the dead job first — `force_rerun=True` only wipes the *remote* stage dir, reusing the same local one, so anything not salvaged before resubmitting risks being overwritten by the replacement's own synced output) only if `RemoteInfo.resubmit_killed_jobs=True` (default `False` — a killed job often needs different resources, not just an identical retry). `cleanup_jobs()` only calls `mark_processed()` on terminal-status jobs, never on one still ongoing after resume retries are exhausted — `'processed'` is excluded from expyre's own restart-reattachment logic, so marking a possibly-still-running job processed would permanently orphan it.

**PyTorch triton requirement**: Recent PyTorch versions ship native triton-backed GPU ops via `torch._native` (confirmed present in torch 2.13). Triton JIT-compiles CUDA extensions at runtime, which requires `python3-dev` (Python headers) on the compute node. HPC compute nodes typically do not have these headers. Fix: set `TRITON_CACHE_DIR` to a persistent path in the `mlip_committee` `pre_cmds` and pre-warm the cache once in an **interactive GPU job** (not the login node — the login node driver may be too old). `mlip/mace/trainer.py` logs a WARNING at import time if `torch._native` is detected and `TRITON_CACHE_DIR` is not set. Pre-warm command (run inside an interactive GPU job): `TRITON_CACHE_DIR=/fhi/home/jholl/.triton_cache python -m mace.cli.run_train --help`

**Loop reports** (`analysis/report/`, user docs `docs/reports.md`): `finish_loop` calls `write_loop_report(self, loop)` (`general.report`, default true; wrapped so a report failure never fails the loop), writing `results/reports/al_loop_N/{report.md, report.json, plots/}` and `results/reports/latest.md`. `stats.py` builds a JSON-safe stats dict from the DB, `high_accuracy_eval_results.xyz` (`geometry_steps`, `geometry_max_steps`, `dft_wall_time_s` recorded remotely by `utils/dft_utils._run_go/_run_sp`), each fit's `evaluation_metrics.json`, `alomancy.log` timings and `events.jsonl`. Issues: `triggers.py` (one `@trigger("name")` function per measurement, returns `None` or `{"value": ..., ...}`) + `suggestions.yaml` (package data: `threshold`/`severity`/`suggestion` template per trigger; `general.report_suggestions` overrides entries key by key) + `rules.py` (never raises over a bad entry; a test enforces triggers == entries). Module sections: optional `report_section` registry entry point (thin lazy wrapper in the module, implementation in `report/sections.py`, `plots_dir=None` when `general.plots` is off); workflow sections: `ActiveLearningWorkflow.report_sections(stats, plots_dir)`. `prepare_run` saves `results/run_config.yaml` so `alomancy report [--loop N|--all] [--config]` (`cli/report.py`) can rebuild reports offline.

**Remote deployment**: ExPyRe serializes functions **by reference** (module path + function name). The remote machine imports the module to resolve the function at run time. When changing the signature or body of any function submitted remotely (e.g. `mlip/base.run_training`, any `ALomancyTrainer` subclass), you must reinstall the updated package on the remote machine (`pip install -e .` there) before restarting, or jobs will import the old code and fail with a `TypeError` at the call site — typically hours after submission.

**Nested `srun` must not request its own `--mem`**: `_build_srun_command` (`utils/dft_utils.py`) launches the DFT/MLIP binary via `srun` from inside the job's own batch script, and requests `--mem=0` — Slurm's documented sentinel for "use all memory already granted to the job." Do not change this to an explicit sub-amount (e.g. `--mem={max_mem_per_node}`): on Slurm configs where the running batch script is accounted as the job's first step and credited with the job's *entire* memory allocation, a nested step's own explicit request competes with that reservation and fails immediately with `"Unable to create step ... Memory required by task is not available"` — regardless of how much memory the job was granted or how small the request is. The job-level memory ceiling belongs on the outer `#SBATCH --mem` line (see next paragraph), not on the inner `srun`.

**HPC wizard memory headers are per-partition**: `add_hpc_wizard()` (`cli/add_hpc.py`) collects `max_mem` per partition and bakes each partition's own `#SBATCH --mem=<N>M` line into that partition's `header` entry in `~/.expyre/config.json` (via `_with_partition_mem_headers`), not into the system-wide header. ExPyRe applies a partition's `header` list in addition to the system-wide header for any job that lands on it. A single blanket `--mem` shared across all of a system's partitions is wrong whenever those partitions have different node memory sizes — it under-requests on large-memory partitions or gets jobs rejected outright on small ones. `node_info.max_mem_per_node` in `~/.alomancy/hpc_config.yaml` is descriptive metadata only; it does not drive any `#SBATCH`/`srun` `--mem` value.

### Key conventions

- **Tabular data uses polars, never pandas** (pandas is not a dependency). Polars has no index: whatever pandas code used as an index is an explicit column (`al_loop` for per-loop metrics, `epoch` for training curves, `loop` for timing, `structure_index` for committee std-devs). Use `.is_empty()`, `.to_list()`, `df.row(i, named=True)`, and `.cast(pl.Float64).to_numpy()` for nullable numeric columns.

- All file I/O uses `extxyz` format via ASE's `read`/`write`.
- **Empty `atoms.info` values don't survive two extxyz round trips**: ASE writes `[]` as `"_JSON []"`, reads it back as an empty array, writes that as a bare `key=`, and reading a bare `key=` takes the next `key=value` as its value. This made `quality_filter_reasons=[]` swallow `model_energy` in every `test_pred.xyz`, so test parity plots vanished. `utils/clean_structures.drop_unwritable_info` strips empty lists/tuples/arrays/strings; `GlobalDatabase._atoms_from_container` and `ALomancyTrainer.evaluate` call it. Any new path that writes xyz from atoms it did not get from the DB should call it too.
- Energy and force labels stored in `atoms.info["REF_energy"]` and `atoms.arrays["REF_forces"]`. **Never use bare `"energy"` as an info key** — ASE moves it to the calculator on extxyz read, losing it from `atoms.info`.
- Structures that need geometry optimisation carry `atoms.info["needs_relaxation"] = True`. **This flag is never cleared automatically** — it survives `atoms.copy()` (and `clean_structures`'s `structure.info.copy()`) through GlobalDatabase storage and back out again. If a `needs_relaxation=True` structure is later reused as an MD seed, every MD trajectory frame derived from it inherits the flag too. Any code path whose output has a fixed, deliberate relaxation policy (e.g. `ActiveLearningWorkflow.high_accuracy_evaluate`, which sets it from `force_ceiling` for every AL-generated structure) must explicitly set `needs_relaxation` on its output rather than relying on whatever value it inherited from an upstream copy.
- `config_type` in `atoms.info` tracks provenance (e.g. `"initialization"`, `"init_dimer"`, `"high_sd"`). Structures selected by the AL loop uncertainty criterion get `config_type="high_sd"` (set by `clean_structures` in `committee_uncertainty_workflow.run()`); the per-loop index is stored separately in `atoms.info["al_loop"]` via `extra_metadata`. Do not use `"al_loop_N"` as a config_type — the loop number is not embedded in the type string.
- The `seed` parameter (default `803`) is used everywhere randomness appears for reproducibility.
- `run_md` (`structure_generation/md/md_wfl.py`) takes `ensemble: "nvt" | "npt"` (default `"nvt"`) plus `pressure` (GPa, only used for `"npt"`) via `structure_generation.run_md_kwargs` in the config. `"nvt"` runs fixed-cell `ase.md.langevin.Langevin`; `"npt"` runs `ase.md.langevinbaoab.LangevinBAOAB` with a variable cell targeting `pressure`. An unrecognized `ensemble` string raises `ValueError` immediately rather than leaving the dynamics object unset. **`LangevinBAOAB`'s `externalstress` must never be passed as `None` for the NPT path** — ASE only activates its barostat (cell momentum steps, cell Langevin thermostat) when `externalstress is not None`; passing `None` silently degrades "npt" to fixed-cell dynamics indistinguishable from `"nvt"` but running the more expensive BAOAB integrator for no benefit. `run_md` derives it as `-pressure * ase.units.GPa` (ASE's stress-is-negative-of-pressure convention), so even the default `pressure=0.0` yields `externalstress=0.0` — not `None` — keeping the barostat live and targeting zero external pressure.
- `select_initial_structures` (`structure_generation/select_initial_structures.py`) reuses structures with replacement when `num_of_md_starts` exceeds the number of structures passing the `chem_formula_list`/`selectable_configs`/`atom_number_range` filters — it no longer raises. Each of the `num_of_md_starts` returned atoms gets a distinct `atoms.info["md_seed"] = seed + i`, which `run_md` (`structure_generation/md/md_wfl.py`) reads to seed Langevin's `rng`; without this, two concurrent MD jobs started from the same duplicated structure would (depending on process-level RNG state) risk producing identical or under-diverged trajectories. A `ValueError` is only raised when the filtered pool is empty (nothing to reuse from at all).
- **MD seeds are reproducible, saved, and replaced once if their run never starts** (`structure_generation/md/md_wfl.py: generate`). `select_diverse_seeds` (`utils/seed_selection.py`) draws from `np.random.default_rng(seed)` (formulas sorted first, since set order varies between processes), and the chosen seeds are written to `structure_generation/md_seeds.xyz` so a restart resumes the same runs: run `i` is always `md_output_i` with `seeds[i]`, and only runs with no output directory are submitted. A run whose trajectory has fewer than `_MIN_FRAMES` (2) frames completed no MD step (every run writes its starting structure first) and gets **one** replacement: a structure not used yet (by `geometry_digest`; reused with a fresh `md_seed` if none are left), appended to `md_seeds.xyz` tagged `info["replaces"] = i` and run as a new index. Runs that did step are kept however short — partial trajectories are real candidates (`run_md` appends frames as it goes and catches force/integration failures). The candidates cache (`<name>_generated_candidates.xyz`) is written only after the replacement round, from runs with ≥ 2 frames; if none have any, `generate` raises `RuntimeError` and writes no cache, so the next restart retries instead of reloading an empty file forever.
- **Generation and selection sizes are separate**: `structure_generation.num_of_structures_to_generate` is the generator's candidate pool (MD: `snapshot_interval = steps × runs // to_generate`), `general.num_of_structures_per_loop` (default 50, `self.num_of_structures_per_loop`) is what every selector sends to DFT. `__init__` (`_resolve_structure_counts`) defaults to_generate to 10 × per_loop in `jobs_dict` (the old MD sampling), raises if to_generate < per_loop, and warns (`few_candidates_configured`) below 2 × per_loop; `generate_candidates` warns (`few_candidates_generated`) when fewer than 2 × per_loop candidates survive the bond filter. The old `structure_generation.desired_num_of_structures` is in `_MOVED_KEYS`. `find_high_sd_structures` takes the count as `num_of_structures` and, when fewer candidates survive than requested, logs a WARNING (`fewer_candidates`) and selects them all; a `ValueError` is raised only for an empty `structure_list` or a count ≤ 0.
- **Structure generators drive their dynamics with the MLIP that `training.trainer` trained, never one of their own choosing**: `generate_candidates` passes the generator a `CalculatorSpec` (`mlip/base.py`: trainer name, training config, model path; built by `ActiveLearningWorkflow.calculator_spec`), not a model path. It is plain data so it pickles into remote jobs (a live, often GPU-resident calculator must not cross the ExPyRe boundary); `spec.build(device=None)` calls the trainer's `get_calculator(model_path, *, device=None)` wherever the calculator is needed — on the node for MD (`md_wfl._run_md_with_spec`), in the driver on the CPU for EZGA. `run_md` takes the calculator as a required argument and has no MACE fallback. The old `md_kwargs.trainer`/`trainer_config` (default `"mace"`) made a SevenNet run hand its `.pth` checkpoint to MACE (`'dict' object has no attribute 'to'` in every MD job); they are in `_REMOVED_KEYS`. `tests/core_tests/test_active_learning_workflow.py::test_md_explores_with_the_calculator_of_the_trained_mlip` guards this end to end. MD/EZGA changes need a remote reinstall.
- **EZGA is an alternative candidate-generation method to MD, selected via `structure_generation.generator: "ezga"`** (default `"md"`). Unlike MD (`md_remote_submitter`, submitted to HPC), `run_ezga` (`structure_generation/ezga/generate_structures.py`) runs entirely in the **local driver process** — no remote submission — and relaxes candidates with the trained model's own calculator on the CPU (`trained_model_calculator`, named in the generated `ezga_config.yaml`, reads the model's `CalculatorSpec` from `calculator_spec.json` — EZGA's YAML loader imports any string containing `:` or a dotted name, so the trainer config can't be inlined — and wraps the calculator in EZGA's generic `ase_calculator`), a real performance cost worth knowing about before pointing it at a large population/generation count. It uses only the single best-fit committee model (the `rank_committee` pick, same one MD uses) as its internal potential; the remaining committee members still score the returned candidates' uncertainty afterward via the normal `all_maces_remote_submitter` path — EZGA only replaces *candidate generation*, not the rest of `generate_structures`' pipeline (bond-distance filtering, committee force-std-dev scoring, etc. all still apply to its output exactly as they do to MD trajectory frames). Configured via `structure_generation.ezga_kwargs`: `max_generations`/`population_size` (both default `2`), `min_atoms`/`max_atoms` (default `2`/`41` — every seed structure must already fall within this range or `run_ezga` raises `ValueError` before ever calling into EZGA), and `mutation_operators` (a dict overriding any of the 5 named operators — `rattle`, `random_strain`, `add`, `remove`, `remove_add` — each independently enable/configurable; an unknown operator key raises `ValueError`, and disabling all of them raises `ValueError` too, since EZGA needs at least one). `bounded_mutation_add`/`bounded_mutation_remove` wrap EZGA's raw `add`/`remove` mutations with an ALomancy-side atom-count clamp (return `None`, i.e. a no-op mutation, rather than producing a structure outside `[min_atoms, max_atoms]`) since EZGA's own primitives don't respect these bounds. `objective_energy_per_atom` treats un-evaluated seeds' NaN energies as `0.0` (matching EZGA's own semantics for not-yet-scored population members) rather than propagating NaN into the objective. Output lands in `results/<base>/<structure_generation_name>/ezga/`: `initial_population.xyz`, `ezga_config.yaml`, `ezga_candidates.xyz`, plus EZGA's own population database (`db`/`db_ro`).
- `verbose` is an int: `0` = silent, `>0` = progress prints.
- The global DB lives at `results/global_database/` (configurable via `db_path` in `CommitteeUncertaintyWorkflow.__init__`). Only DFT-evaluated structures (with `REF_energy`/`REF_forces`) are stored in it.
- Every structure in `GlobalDatabase` carries `atoms.info["global_db_id"]`: a zero-based integer index assigned at insertion time, stable across sessions. Call `db.assign_global_db_ids()` to backfill existing DBs.
- `general.remove_redundancy` (default `True`) runs after initialization and after each AL loop to prune similar structures before the next training round (the train/test quality filters run right after it — see the `split_filter` bullet). Redundancy descriptors (`char_vec`, `global_descriptor/atomic_distance_descriptor.make_char_vec`) are **cached in the DB** under a dimension-specific container-metadata key (`char_vec_128`, `remove_redundancy.descriptor_key`) via `GlobalDatabase.store_descriptors`, so each structure's descriptor is computed once, not on every loop/restart; `_atoms_from_container` strips every `char_vec*` key so they never reach `atoms.info` or train xyz files. `remove_redundancy_from_partition` (`utils/remove_redundancy.py`) derives its descriptor-space tolerance from the data via `NaturalTolerancePlateauProbe` (`condition="minimum"`) rather than a fixed value. It skips dedup entirely, flagging nothing, when the probe raises `ValueError` (too few structures) or warns "No plateaus found", rather than applying the probe's arbitrary midpoint fallback. Its `tolerance` parameter is vestigial and ignored.
- `CommitteeUncertaintyWorkflow.select_uncertain` uses `best_model` (`rank_committee`: lowest common-validation `mae_f`, from each fit's `evaluation_metrics.json`) as the MD base model; all other fits form the uncertainty comparison committee. The best model is predicted once, labelled `"base_mlip"`, and every other model under its own `fit_i` label, so it isn't double-counted in the std-dev computation.
- Energy MAE reported as `mae_e_per_atom` (eV/atom) everywhere — `mlip/evaluation.py`, `plotting.py`, and `mlip_plots.py` all use this key. Never use `mae_e` (total energy per structure) in plots; it has similar magnitude to `mae_f` and causes visual confusion.
- **No plotting path may be interactive**: `alomancy/__init__.py` calls `matplotlib.use("Agg")` before any submodule can import `matplotlib.pyplot`, since `RemoteJobExecutor.run_all_jobs_bounded` polls jobs from a `ThreadPoolExecutor` and any `Figure` created under an interactive backend (matplotlib's default whenever `DISPLAY` is set, e.g. `TkAgg`) that gets garbage-collected on a worker thread crashes the whole process with SIGABRT (Tkinter finalizers calling back into Tk from the wrong thread). Every plotting function creates a figure, saves it, and closes it (`plt.savefig` + `plt.close(fig)`) — never `plt.show()`. `analysis/plotting.py`'s `Plot` class has no `show()` method for the same reason; `Plot.save()` closes its own figure after writing.
- **`_ensure_expyre_db_thread_safe`'s lock must cover the fetch, not just the query**: `_locked_execute` (`remote_submission/executor.py`) patches `JobsDB._execute`, expyre's sole low-level sqlite access point. `self.db.execute(cmd)` returns a live, unfetched `sqlite3.Cursor` — every caller in expyre's `jobsdb.py` only consumes it *afterward* (`list(self._execute(...))`, `for row in self._execute(...)`). Releasing the lock right after `execute()` returns (rather than after the rows are actually fetched) leaves a window where a second thread's own `execute()` call on the same shared connection (`check_same_thread=False` disables sqlite3's same-thread assertion, not genuine concurrent-cursor safety) can corrupt the first thread's still-pending read, silently yielding zero rows for a row that genuinely exists — this was the real cause of a production `list(config.db.jobs(id=...))[0])` `IndexError` (`expyre/func.py`) from a *single* process with many concurrent job-monitoring threads (e.g. `structure_generation` polling ~20 MD jobs at once), not cross-process contention as originally suspected. `_locked_execute` now materializes the cursor into a `list` *inside* the lock before releasing it. `_get_ssh_call_lock`/`acquire_local_expyre_lock` (`threading.Lock`/`fcntl.flock` respectively) remain thread- and process-scoped defenses against a *different* class of contention (concurrent ssh sessions on one host; two alomancy processes sharing one `local_stage_dir`) — neither was the cause of this specific bug. `_run_single_job`'s failure handler logs the full traceback at DEBUG level (`results/alomancy.log`) for any future `IndexError`/similar failure, which is what made this one identifiable from a production log instead of needing source-level archaeology.
- **Every AL run gets its own isolated ExPyRe job-tracking state by default**: `alomancy/__init__.py`'s `_ensure_local_expyre_root` runs at package-import time (before anything can import `expyre.config` and trigger its own one-time resolution) and copies ALomancy's canonical HPC systems config — `configs/global_config.py`'s `EXPYRE_CONFIG`, i.e. `~/.alomancy/expyre_config.json`, written by `alomancy add-hpc` — into a fresh `<rundir>/.expyre/config.json`, unless that directory already has a `.expyre`/`_expyre` (idempotent) or `EXPYRE_ROOT` is set explicitly (bypasses expyre's directory walk entirely, so a run-local `.expyre` would never be consulted). expyre's own config resolution walks from cwd up to `$HOME`, merging every `.expyre`/`_expyre` it finds and using the *deepest* one as `local_stage_dir` — the directory holding both `jobs.db` and every job's stage directory (`ExPyRe.__init__`'s `tempfile.mkdtemp(dir=config.local_stage_dir)`) — so a run-local copy becomes the one actually used, isolating this run's job state from every other alomancy run on the same machine or shared home directory. It's a one-time snapshot, not a live reference: editing `EXPYRE_CONFIG` later doesn't retroactively affect a run whose `.expyre/` already exists. `write_expyre_config` (`cli/add_hpc.py`) migrates one-time from `LEGACY_EXPYRE_CONFIG` (`~/.expyre/config.json`, the pre-isolation location) the first time it writes `EXPYRE_CONFIG` and finds it missing, so systems configured before this existed aren't lost — raises `ValueError` rather than silently dropping data if the legacy file it's migrating from turns out to be corrupt, matching how a corrupt canonical file is already handled. `alomancy nuke`'s default target (`cli/nuke.py`'s `resolve_default_expyre_dir`) resolves the same way, falling back to `~/.expyre` only if no local config has been resolved yet — so nuking from inside a project directory only clears that project's own job state. `resolve_hpc_host` (`utils/remote_ssh.py`, used by the workflow-startup remote-version check and `alomancy upgrade-hpc`) tries `EXPYRE_CONFIG` then falls back to `LEGACY_EXPYRE_CONFIG` too — every reader of ExPyRe's systems config must fall back the same way, or an installation that hasn't re-run `alomancy add-hpc` since upgrading silently loses that reader's ability to find its HPC systems.
- **`acquire_local_expyre_lock`** (`remote_submission/executor.py`), called at the start of `pre_run_checks()` before any remote submission: takes an exclusive, non-blocking `fcntl.flock` on `expyre.config.local_stage_dir`, raising `RuntimeError` immediately if another alomancy process already holds it (a no-op if this process already holds it, or if `local_stage_dir` hasn't resolved yet). POSIX-only, matching this codebase's Linux/HPC-only environment. Unlike a hand-rolled PID-file check, the OS releases an `flock` automatically the instant the holding process's file descriptor closes — including on a crash or `kill -9` — so a dead process never leaves a stale lock blocking a legitimate restart. The lock file records `pid`/`host`/`started` for diagnostics if a conflict is hit. The check-and-set of its module-global lock handle is itself guarded by `_expyre_root_lock_guard` (double-checked locking, matching `_get_ssh_call_lock`'s pattern) — `flock` is scoped per *open file description*, not per-process, so two threads racing this function in the same process could otherwise each open a fresh file description and have the second one fail against the first's already-held lock, incorrectly reporting itself as a conflicting process.
- **`RemoteInfo.lock_timeout` defaults to `None` (wait indefinitely for the per-host ssh-call lock, `_get_ssh_call_lock`), not derived from the job's `max_time`.** A prior version set it from `max_time` so a `RemoteJobExecutor` worker thread queued behind another one stuck on an interactive ssh password/OTP prompt would give up and fail loudly after that duration rather than just waiting — but the thread genuinely *holding* the lock and blocked on that prompt was never bounded either way (no timeout exists anywhere on the underlying `subprocess.Popen(...).communicate()` call inside `expyre`), so the revert only ever turned "everything queued behind it waits quietly, exactly as long as it takes someone to type the password" into "everything else fails loudly around the one thing that's still just waiting." Reverted to the pre-existing behavior. `pre_run_checks()`'s `ensure_ssh_connectivity` (`utils/remote_ssh.py`) is the actual fix for the underlying problem this was trying to guard against: it runs a bare `ssh <host> true` (no `timeout=`, no `capture_output=`, so a password/OTP prompt prints to and reads from the real terminal) once per distinct HPC host configured in the run, before any remote submission begins — while whoever launched the run is presumably still at the terminal to answer it, rather than however many hours later a background worker thread first happens to touch that host unattended. If the host's ssh config uses connection multiplexing (`ControlMaster`/`ControlPersist`), authenticating here establishes the shared control connection once so every later call from `RemoteJobExecutor` reuses it silently. Never raises — an unreachable host is logged as a warning and left for the real remote submission to fail loudly on later.
- Initialization config uses individual counts (`num_of_dimers_per_combo`, `num_of_trimers_per_combo`, `num_of_amorphous_structures`, `num_stretch_compress_per_mp`) rather than the old `d_t_s_a_ratio` + `target_non_mp_structures_to_add`.
- `creation_kwargs.max_num_of_atoms` and `creation_kwargs.num_of_atoms_per_amorphous` are separate knobs (both default to `20`): `max_num_of_atoms` caps atom count for Materials Project fetches (`atoms_list_from_mp`'s `max_num_atoms`), `num_of_atoms_per_amorphous` sets the target atom count per generated amorphous cell (`create_amorphous_atoms_list`'s `atom_number`). They used to be the same value (`max_num_of_atoms` drove both); changing one no longer affects the other.
- `creation_kwargs.mp_max_energy_above_hull` (default `0.1` eV) sets the energy-above-hull cutoff for Materials Project fetches (`atoms_list_from_mp`'s `max_energy_above_hull`), previously hardcoded. Only affects MP structures, not amorphous/dimer/trimer generation.
- `IsolatedAtom` and `init_MP` config_types are deduplicated by `(config_type, formula)` in `GlobalDatabase.add_structures()`; other config_types (dimers, trimers, amorphous, AL loop structures) are always added without exact dedup.
- **`general.start_from` picks the start mode from which keys are present** (`_parse_start_from`, `core/committee_uncertainty_workflow.py`; user docs: `docs/starting_a_run.md`): `train_xyz`+`test_xyz` (import both, keeping the file-level split), `xyz` (one path or a list; imported, then split), `database` (import a **copy** of a former run's `GlobalDatabase` via `GlobalDatabase.import_from_database` — keeps `config_type`/`split`/duplicate and high-force flags, old `global_db_id` → `source_global_db_id`, `model_*`/`mace_*` predictions dropped, source never written), or none (cold start). More than one source, half a train/test pair, unknown keys, or `metadata_map` without an xyz source raise `ValueError` at construction. **Every mode then takes the same DB-driven path** in `_initialize_training_set`: `_import_start_data` (idempotent — xyz files by `source_dataset_sha256`, databases by `source_database`) → `compute_needs` → generate/DFT only the missing initialization targets → split → write `results/initialization/train_set.xyz`/`test_set.xyz`. The split keeps any structure's existing `split` tag (pre-split files, imported DBs) and applies the `test_ratio`-over-`target_config_types` rule (`_split_untagged`) only to untagged structures; other tags (e.g. `diagnostic`) stay out of both sets. xyz imports go through `utils/import_structures.normalize_metadata` first: labels are mapped from `metadata_map`, then aliases (`type`/`label`/`config`, `energy`/`dft_energy`, `forces`/`dft_forces`, ...), then the attached calculator; missing `config_type` → `"external"`; missing energy/forces raise before any import or DFT; structures with any element outside `general.elements` are dropped at import (`filter_by_elements`, xyz and `database` modes alike, WARNING event `start_from_elements_excluded`), so redundancy removal and the train/test filters never see them, and widening `elements` later won't re-import them (the source is already marked imported: `GlobalDatabase.record_import` writes every source to `imported_sources.json` next to the DB, even when every structure was excluded, and `is_imported` also accepts the older per-structure markers); the writing run's `split`/`global_db_id`/flags/`model_*` predictions are always dropped. A single-xyz start whose structures are all `"external"` (not in `target_config_types`) raises rather than silently producing an empty test set. The old entry points (`initial_train_file_path`/`initial_test_file_path`, `initialization.extra_datasets`, `skip_initialization`, `reset_extra_splits`) are in `_REMOVED_KEYS` and raise with their replacement.
- `jobs_dict["high_accuracy_evaluation"]["name"]` must equal `"high_accuracy_evaluation"`. `ase_remote_submitter` always writes output to the hardcoded path `results/<base>/high_accuracy_evaluation/batch_N/`; the result-collection glob in `high_accuracy_calc_interface.high_accuracy_evaluation` uses `output_name` (i.e. the `name` field) as the subdirectory. If they diverge the glob finds nothing, an empty sentinel is written, and the phase is permanently marked done with zero structures.
- Guard user config errors in functions that run remotely with `if`/`raise ValueError(...)`, not `assert`. Python's `-O` flag (common in HPC module environments) strips all asserts silently, deferring config failures to the remote job hours after submission.
- **`qe_kwargs` merges into QE's defaults per namelist, never by replacing a whole namelist**: `get_qe_input_data` (`high_accuracy_evaluation/dft/run_qe.py`) merges each user namelist (`control`, `electrons`, ...) key-by-key into its defaults. It used to do a top-level `{**defaults, **qe_input_kwargs}`, so `qe_kwargs: {control: {tstress: false}}` silently dropped `control.tprnfor`/`calculation`; QE then never printed forces and every DFT job in a production AL loop failed with `forces not present in this calculation`. `get_qe_input_data` runs on the remote node, so changes to it need a remote reinstall (see "Remote deployment").
- **Required config is validated at construction, not at first use**: `CommitteeUncertaintyWorkflow.__init__` raises `ValueError` if `general.committee_uncertainty_kwargs` lacks `test_ratio` or `target_config_types` (`_COMMITTEE_UNCERTAINTY_REQUIRED`), and logs a WARNING for any unrecognised `general` key (`_GENERAL_KNOWN_KEYS`, catches typos like `skip_initializatoin`). `test_ratio` is otherwise first read only after an AL loop's DFT finishes, hours into a run.
- **`high_accuracy_evaluation` never marks itself done with zero results after submitting jobs**: if structures were submitted and no results exist at all (none from this batch, none from earlier batches), it raises `RuntimeError` instead of writing `high_accuracy_eval.done`/an empty `high_accuracy_eval_results.xyz`. Otherwise the loop would permanently record zero new structures on restart. A partial failure (some results collected) still completes normally.
- **VASP pseudopotentials**: ASE's `Vasp` calculator reads POTCAR locations only from the `VASP_PP_PATH` environment variable — there is no constructor kwarg for it. `create_vasp_calc_object` (`high_accuracy_evaluation/dft/run_vasp.py`) sets `os.environ["VASP_PP_PATH"] = hpc["pp_path"]` before building the calculator whenever `pp_path` is present in the HPC profile. `pp_path` must point at the directory *containing* `potpaw_PBE`/`potpaw_LDA`. Elements without a `pseudo_dict` override fall back to the default (unsuffixed) POTCAR under that path; if the library doesn't carry a given element, VASP fails with `No pseudopotential for <element>!`.
- **VASP requires full periodicity**: ASE's `Vasp` calculator rejects any `pbc` other than `[True, True, True]` — VASP has no non-periodic mode. Non-periodic structures (isolated atoms, dimers, trimers from initialization) are padded with vacuum and forced to `pbc=True` by `_ensure_fully_periodic` inside `create_vasp_calc_object` before the calculator is built. QE's `Espresso` calculator handles non-periodic cells natively and needs no equivalent step.
- **`generate_structures`' `high_sd` output (MD or EZGA) is relaxed (GO) until its max force is at most `high_accuracy_evaluation.force_ceiling` rather than evaluated at a single point, whenever a ceiling is set** (the default, `100.0` eV/Å, `_DEFAULT_FORCE_CEILING`; explicitly `null` means single point only). `force_ceiling` is a cap, not a convergence target: structures are relaxed only far enough to get below it. It applies to AL-generated structures only — initialization structures (including deliberately compressed dimers/trimers) keep their own `needs_relaxation`/fmax 0.05 policy. It replaced the DFT half of the removed `general.high_force_threshold` (in `_REMOVED_KEYS`); the other half is `general.train_filter.max_force`. Root cause this fixes: a cold-start committee can drive MD/EZGA into near-collision, wildly-off-equilibrium geometries whose raw single-point forces are enormous (observed: median ~440 eV/Å, max ~1680 eV/Å on one production run) and get discarded anyway by the train quality filter — training-set growth stalls even though the DB keeps growing, since almost nothing survives that filter. Relaxing first turns that wasted DFT compute into a genuinely useful, moderate-force training point instead. `force_ceiling` is injected into the `high_accuracy_evaluation` job dict as `"fmax"` (`committee_uncertainty_workflow.py`'s per-loop `run()` call — this call site previously never passed `allow_relaxation=True` at all, so `needs_relaxation` was completely inert for this path regardless of its value); `_run_go` (`utils/dft_utils.py`) reads `job_dict.get("fmax", 0.05)` and the analogous `job_dict.get("max_num_of_relax_steps", 200)` (an independent, optional config key, not tied to `force_ceiling`) for its BFGS step budget. Non-convergence within that budget is not a failure: `_run_go` logs a warning and keeps the best structure BFGS found (`atoms.info["geometry_converged"] = False`) rather than discarding the completed DFT computation — the train quality filter (`train_filter.max_force`) remains the correct backstop for whatever residual force that partial relaxation leaves behind. `initialization`'s own structures are untouched — they already carry their own correct `needs_relaxation` per structure type.
- **Train/test quality filters (`general.train_filter` / `general.test_filter`, `utils/split_filter.py`)**, identical schema: `max_force` (eV/Å; max per-atom force norm ≥ value, or missing/non-finite forces, fails) and `formation_energy_per_atom` (`[min, max]` eV/atom, inclusive, either bound null = open; `(E − Σ E0[element]) / n` against the DB's `IsolatedAtom` energies — the parity plots' definition — stored as `REF_formation_energy_per_atom_e0`). Defaults (`TRAIN_FILTER_DEFAULTS`/`TEST_FILTER_DEFAULTS`, merged under the user block by `resolve_split_filter`): train `max_force: 100` (the protection the removed `high_force_threshold` gave), everything else off; an explicit `null` disables a default. `apply_split_filter` runs from `CommitteeUncertaintyWorkflow._apply_split_filters` after every redundancy pass and **rewrites `is_quality_filtered`/`quality_filter_reasons` on every container of the split each time**, so loosening or disabling a filter brings structures back. Failing structures stay in the DB; `get_train_atoms`/`get_test_atoms` skip them (`exclude_quality_filtered=True`). Structures with an element missing from the E0 dict are not energy-filtered (one warning per call). The legacy `is_high_force` flag from older DBs is ignored everywhere. Validated at construction (`validate_split_filter`, `ValueError`).
- GO (geometry-optimisation) and SP (single-point) structures in `high_accuracy_evaluation` share a single batch dir and a single `ase_remote_submitter` call (`batch_num = current_batches`, the count of existing `batch_*` dirs — still needed for restart-safety, to avoid colliding with a prior partial run). They're no longer split into separate batches; `per_structure_function` picks `run_go` or `run_sp` per structure from its own `needs_relaxation` flag, and both kinds roll through the same `RemoteJobExecutor` pool, distinguished only by a `go_`/`sp_`-prefixed job name. If any structure in the batch needs relaxation, the shared `RemoteInfo`'s walltime is built from `max_go_time` (the GO ceiling) rather than the plain `max_time`, since SP jobs finishing early under a longer walltime is harmless but a GO job running under an SP-sized one is not.
- `max_num_of_concurrent_jobs` (HPC profile, `~/.alomancy/hpc_config.yaml`, default `20`, set via the `alomancy add-hpc` wizard) caps how many jobs a `RemoteJobExecutor` keeps started at once — see `RemoteInfo`/`get_remote_info` (`configs/remote_info.py`). The old job-dict-level `max_batch_size` fallback was removed in 1.0.0 and is ignored; profiles still using the pre-rename key `max_concurrent_jobs` are honoured with a warning (`_resolve_max_concurrent_jobs`). This is unrelated to `structure_generation`'s `num_of_md_starts` (`select_initial_structures.py`), which controls how many seed structures are selected for MD, not scheduler concurrency.
- **Model prediction files**: after training, `ALomancyTrainer.evaluate` (`mlip/base.py`, on the remote node) writes `train_pred.xyz`/`test_pred.xyz` (and `valid_pred.xyz`) in `results/<base>/training/fit_<i>/`, carrying `model_energy` (float, eV) and `model_forces` (array, eV/Å) — generic keys, not MACE-specific. `read_predictions` (`mlip/base.py`) reads them locally; `_store_predictions_and_cleanup` stores them in the GlobalDB via `store_model_predictions` (`model_energy_loop_{N}_fit_{i}` / `model_forces_loop_{N}_fit_{i}`). `plot_dft_vs_model` reads from DB first, then falls back to these files, then skips with a blank subplot — **never runs local calculator inference**. **For MACE, evaluation uses the uncompiled `{name}_stagetwo.model` (`MaceTrainer.model_path`), never the TorchScript-compiled one**: the compiled model's force evaluation (`torch.autograd.grad` through the TorchScript interpreter) raised `RuntimeError: ... Global alloc not supported yet` for every multi-atom structure on one production GPU/CUDA/PyTorch combination, silently degrading every parity plot to one point. MACE writes the uncompiled model unconditionally but the compiled one inside a bare `except Exception: pass`, so restart checks (`output_paths`) also gate on the uncompiled model; the compiled one is only `deployable_model_path` (copied to `results/best_model/`).
- **Checkpoint cleanup must also run locally**: `ALomancyTrainer.train` runs `cleanup()` on the remote node (MACE: deletes `checkpoints/` once the compiled model exists), but ExPyRe's periodic mid-training sync (`get_remotes()`, every `get_results()` poll) pulls the remote stage directory back with `delete=False` (additive only), so every epoch-numbered checkpoint MACE ever wrote accumulates locally (observed: 5–7 GB per fit). `_store_predictions_and_cleanup` therefore calls `trainer.cleanup(fit_dir)` again on each fit's local copy after training. Succeeded jobs' stage directories are then wiped by `cleanup_jobs`, so what a run keeps is what survives `cleanup_paths` in `results/`: for MACE `checkpoints/` plus the never-read stage-one `<name>.model`/`<name>_compiled.model` (~88 MB each) go once the compiled stage-two model exists (a fit drops from ~384 MB to ~210 MB, mostly the two stage-two models and `train_pred.xyz`); for SevenNet every `checkpoint_*.pth`.
- **Dynamic `max_num_epochs`**: `training.mace_kwargs.max_num_epochs` accepts `"dynamic"` (the default when unset) or a positive int. `MaceTrainer.fit` resolves it through `utils/training_schedule.resolve_epochs(configured, batch_size, n_train + n_valid)` — `ceil(200_000 * batch_size / n)`, clamped to `[20, 300]` — counting the validation set too, so resolved counts match earlier versions. The resolved `max_num_epochs`/`start_swa` are written to `resolved_mace_epochs.json` in the fit directory (fixed or dynamic alike); `MaceTrainer.training_history` returns its `start_swa` as `stage_two_epoch` (None for fits trained before the sidecar existed: no Stage 2 line), so the marker is never guessed. `plot_training_curves` takes the marker from the **first successfully-collected** fit, never assuming `fit_0` succeeded.
- **MACE `E0s` reach MACE as a string keyed by atomic number** (`mlip/mace/trainer.py: _mace_e0s_arg`). MACE's own parser (`mace.tools.scripts_utils.get_atomic_energies`) calls `E0s.lower()`/`ast.literal_eval(E0s)` and indexes the result by atomic number, so a dict — the default built from the database's `IsolatedAtom` energies (the workflow passes a trainer-agnostic `{symbol: eV}`), or one written in `mace_kwargs.E0s` with symbol or Z keys — is converted to `"{6: -155.1, ...}"` inside the MACE module only, after the element-coverage check. Strings (`"average"`, a `.json` path) pass through. A test feeds the converted value to MACE's real parser.
- **Stress harvesting vs. stress training are separate toggles**: DFT stress is harvested into `atoms.info["REF_stresses"]` (a Voigt 6-vector, `ase.Atoms.get_stress()`'s default shape — matching exactly what MACE's own `stress_key` reader expects, per `mace/data/atomic_data.py`) by default whenever available — QE's `get_qe_input_data` sets `tstress: True` by default, and `clean_structures` (`utils/clean_structures.py`) captures it non-fatally (stress is not always physically meaningful, e.g. non-periodic structures; a capture failure is tallied and logged as one summary line, never per-structure spam, and never raises). `REF_stresses` is not a native `AtomPositionManager` field (unlike `REF_forces`, which round-trips via `total_force`), so `GlobalDatabase._prepare_for_storage`/`_atoms_from_container` manually serialise it through `info["_REF_stresses"]`. **Training** on stress is a separate, opt-in `training.mace_kwargs.compute_stress` flag (default `False`) — a bare `stress_key` has no training effect on its own (confirmed against `mace/tools/model_script_utils.py`: MACE only computes/uses stress when `loss` is `"stress"`/`"huber"`/`"universal"`). `_apply_compute_stress_defaults` (`mlip/mace/trainer.py`) applies `stress_key="REF_stresses"`/`loss="stress"` via `setdefault` (never overriding an explicit user choice) only when `compute_stress=True`. Kept separate from harvesting (which is default-on) so switching MACE's loss function — a real training-behavior change — never applies silently to an existing production run's next loop.
- **Formation-energy parity plots**: `plot_dft_vs_model` plots *formation energy per atom* (`(E - sum(E0[symbol] for symbol in structure)) / n_atoms`), not raw per-atom energy, whenever a `GlobalDatabase` is available and has `IsolatedAtom` structures — `GlobalDatabase.get_isolated_atom_energies()` builds the `{symbol: REF_energy}` dict once per loop from those, and it is threaded into both `get_mace_predictions(..., e0=...)` (DB tier) and `_parse_eval_xyz(..., e0=...)` (xyz-fallback tier). The same E0 shift is subtracted from both DFT and model energy for a given structure, so it cancels exactly in the reported `mae_e_per_atom`/MAE annotation — it only changes the *shape/spread* of the parity scatter, not the training-curve MAE plots (`mae_al_loop_plot`, `plot_training_curves`), which read `mae_e_per_atom` from each trainer's own training log (via `training_history`) and are untouched by this. Falls back silently to raw per-atom energy (logging one WARNING) when no `GlobalDatabase`/no `IsolatedAtom` entries are available, or when a structure contains an element missing from the E0 dict — this preserves old behavior for pre-formation-energy runs and never mixes formation- and raw-energy points within one figure. `alomancy replot` opens the `GlobalDatabase` at `results_dir/global_database` (matching `GlobalDatabase.__init__`'s default `db_path`) if it exists, so replotted parity plots match the live AL loop's; older results directories without a `global_database/` fall back gracefully.
- **`results/best_model/` always holds the latest loop's best committee member**: at the end of every `train_models` call, `_update_best_model` picks the fit with `rank_committee` (same choice as MD's base model), copies its deployable model (the trainer's `deployable_model_path`, so trainer-agnostic) to `results/best_model/ALomancy_best_model<suffix>` — keeping the trainer's own extension, `.model` for MACE, `.pth` for SevenNet, so a loader chosen by extension gets the right format — via temp file + `os.replace`, deletes any other `*.model` or `ALomancy_best_model.*` there, and writes `model_metadata.json` (`al_loop`, `fit_idx`, `selected_on_split`, `model_file`, `trainer`, source path, sha256, and per-split energy/force/stress errors overall and per `config_type`). Missing evaluations or no compiled model log a warning and leave the previous best model in place — never fails the loop.
- **The MAE-vs-loop plot shows the best committee member per loop, not the committee mean**: `_cross_loop_metrics_dataframe` (live run) and `alomancy results --replot` both use `mlip/evaluation.metrics_by_loop` (`best_fit_test_metrics` per loop) — the `rank_committee` pick's **test**-split `mae_f`/`mae_e_per_atom`, one row per loop with the loop number in an `al_loop` column that `mae_al_loop_plot` uses as its x axis (so a skipped loop shows as a gap). The live aggregator skips a loop with inconsistent evaluations (warning); replot raises (`strict=True`).
- **Parity plots mark the lowest-MAE subplot per column with a gold star** (`_add_best_star`, `analysis/mlip_plots.py`): the energy subplot with the lowest energy MAE and the force subplot with the lowest force MAE — possibly different fits — each get a `★` (`gid="best_star"`) just above the axes' top-left corner, clear of the in-axes MAE label. Train and test figures are starred independently; fits with no predictions never get one.
- **`md_kwargs.traj_interval` (default `None`, off) writes a full-resolution MD trajectory** to `md_output_i/md_trajectory.xyz` (extxyz, every `traj_interval`-th production step, equilibration excluded) alongside the subsampled candidate snapshots, via a `dyn.attach` observer in `run_md`. The observer skips a step it has already written, since ASE re-calls observers at the start of every `dyn.run()` and the snapshot loop calls `run()` in segments. Runs remotely, so changes need a remote reinstall. Validated with `if`/`raise ValueError` (positive int or null).
- **Per-loop plots live in their own subdirectory, `results/current_plots/<base_name>/`** (e.g. `results/current_plots/al_loop_4/`), not flat in `results/current_plots/` alongside every other loop's files. `plot_training_bond_distances`, `mae_al_loop_plot`, `plot_training_curves`, and `plot_dft_vs_model` are each called with that loop's own subdirectory as their `plots_dir`/`directory` argument — the reorg is implemented entirely at the call site (`committee_uncertainty_workflow.py`'s AL loop constructs `loop_plots_dir = plots_dir / base_name` once per iteration; `alomancy.cli.replot` mirrors the same layout, and for its once-per-run cross-loop `mae_al_loop_plot` call — which shows the fullest cumulative history — writes into the *last* plotted loop's subdirectory to match what the live run's final loop would have produced), not inside any of the plotting functions themselves, which are unaware of the directory scheme and still take a `plots_dir: Path` and write into it directly. Filenames are unchanged (still `_al_loop_N`-suffixed, e.g. `training_mae_al_loop_4.png`) — only the directory changed. `plot_training_curves` also writes each fit's per-epoch `loss`/`mae_e_per_atom`/`mae_f` to a `metrics/` subdirectory *under that same per-loop directory* (`results/current_plots/<base_name>/metrics/<base_name>_fit_<i>_training_metrics.csv`), alongside the PNGs rendered from the same DataFrame — the raw numbers behind a plot no longer require re-parsing `*_train.txt`. Run-level aggregate plots — currently only the combined timing plot below — are the one exception: they summarize across all loops, not just one, and stay flat at the top of `results/current_plots/`.
- **`timing_plots` (`analysis/timing_plots.py`) writes a single combined figure, `results/current_plots/timing_combined.png`** — a stacked bar chart of wall-clock time per phase per AL loop (queue/running sub-segments, same data `timing_phases.png` used to show) overlaid with a line on a secondary y-axis (`ax.twinx()`) giving the number of training structures per loop (the information the old, now-removed `timing_total.png` carried as text labels on its own separate bar chart). The legend is at `upper left` and combines both axes' handles in one `ax.legend(h1 + h2, l1 + l2, ...)` call — a bare `ax.legend()` after `twinx()` silently drops the second axis's line from the legend. Bars sit at their real loop numbers and the x axis uses `MaxNLocator(integer=True, nbins=12)`, so ticks are plain loop numbers, thinned out on long runs. Writing the combined plot also deletes any leftover `timing_total.png`/`timing_phases.png` (`_STALE_TIMING_PLOTS`) from the same directory. The figure width is a fixed `figsize=(10, 6)` regardless of the number of loops, unlike the old two-plot version's `max(4, len(loops) * 1.2 + 1)` sizing, which grew unbounded over a long run; bars get more cramped with many loops on a fixed-width figure, an accepted, explicitly requested tradeoff. Same public signature (`timing_plots(log_file, directory)`) as before, called once per loop from `committee_uncertainty_workflow.py` and once from `alomancy.cli.replot` — this is a run-level aggregate, so it is the one plot that stays flat in `results/current_plots/` rather than moving into a per-loop subdirectory.
- `_initialize_training_set`'s `test_ratio` (`_split_untagged`) applies only within the `target_config_types` pool (e.g. `init_amorphous`, `init_MP`), never against the whole DB — dimers/trimers/stretch_compress/`IsolatedAtom` never count toward it. Computing the quota against the full DB could route 100% of a small `target_config_types` pool into test, and since `update_splits_post_hoc` never re-tags an already-tagged DB container, that config_type would be permanently starved out of `train_atoms_list` on every subsequent loop. A backstop still reserves one structure per config_type against an unlucky shuffle leaving one out entirely.
- **`train_models` retries failed fits once, and a fit only counts once it is evaluated** (`ActiveLearningWorkflow._train_models_phase`). After the first `submit_n` batch, every fit index still missing is resubmitted once (same seed, same split files); then `min_successful` is checked (3 for the committee, 1 for random_selection) and fewer raises `RuntimeError`, while more-but-not-all logs "proceeding with N". Success is decided by `_collect_fit` exactly like the restart cache: all of the trainer's `output_paths` exist (for MACE: the uncompiled model **and** `evaluation_metrics.json`) and `read_existing_result` succeeds (checksum-verified). A job that returned a result but left no evaluation (e.g. `_evaluate_and_save_predictions` bailed out) is logged as "finished but was not evaluated" and retried like any other failure, rather than surfacing later in best-model selection. Seeds are recorded (`fit_seed.json`) only for fits that pass this check. Fits are always addressed by their own `fit_idx` (`fit_<i>` directory), never re-derived from a range, so a retry never overwrites a successful fit.
- **Committee ranking (`mlip/evaluation.rank_committee`) uses checkpoint evaluations, not training logs, and raises rather than guessing.** Each fit's `evaluation_metrics.json` (written on the remote node by `ALomancyTrainer.evaluate`) is read through `read_evaluation`, which also requires the evaluated model to exist and match the SHA-256 recorded with the metrics — a missing, unevaluated, or since-modified model counts as a missing fit. It ranks by *metric* (default `mae_f`) on the shared `"valid"` split when every fit has one; when NO fit has one (normal for a small eligible pool — `_select_validation_split` only warns and skips the carve-out) it falls back uniformly to `"test"`. If any fit is missing evaluation on the split being used — including fits that *disagree* on having `"valid"` — it raises `RuntimeError` ("...missing complete checkpoint validation...") instead of picking from whoever remains; there is no `fit_0` default (that once crashed `generate_structures` when `fit_0` itself had failed).
- `RemoteJobExecutor._run_single_job` resumes a job on transient remote-communication failures instead of abandoning it — see the "Remote execution" section above and `docs/remote_submission_architecture.md` §3.3 for the full mechanism.
- `generate_structures`'s reload of an existing `structure_generation_input_structures.xyz` passes `index=":"` to `ase.io.read` — a bare `read()` call defaults to returning only the *last* frame — and validates the reloaded count against `structure_selection_kwargs.num_of_md_starts`, regenerating via `select_initial_structures` if it's short. Guards against a partially-written file (e.g. an HPC filesystem filling up mid-write) being silently trusted and starving `find_high_sd_structures` of candidates several steps downstream.
- **No structure with a pairwise atomic distance below 0.5 Å is ever submitted to DFT**: `filter_structures_by_min_bond_distance` (`utils/clean_structures.py`) is called both in `generate_structures` (before the MACE committee evaluation, not just before DFT — no point scoring an unphysical structure's uncertainty either) and again in `high_accuracy_evaluation` itself (a final safety net that also covers the initialization-bootstrap call site, which has no upstream filter of its own). `get_all_distances(mic=True)` is safe to call unconditionally across every `config_type` (periodic or not); single-atom structures always pass through.
- **Surviving structures are wrapped into their periodic cell immediately before DFT submission**: `wrap_structures_into_cell` (`utils/clean_structures.py`) is called in `high_accuracy_evaluation` right after `filter_structures_by_min_bond_distance` — only structures that already passed that filter get wrapped, since there's no point fixing an unphysical structure's cell positions. Guards against MD trajectories leaving atoms drifted outside the cell (a normal MD artifact, unrelated to the short-bond-distance case the filter above handles); QE/VASP generally expect coordinates within the reference cell. Calls `Atoms.wrap()` unconditionally with no `pbc`-based guard — confirmed empirically against ASE 3.28 that it mutates in place (returns `None`), preserves `atoms.info`/`atoms.arrays`/any attached `atoms.calc` exactly, and is a safe no-op on non-periodic structures (positions on non-periodic axes, or on a `pbc=False` structure with no cell at all, are left unchanged).

### sage_lib / GlobalDatabase internals

`sage_lib.Partition` (hybrid HDF5+SQLite) only persists `atoms.info`, **not** `atoms.arrays`. `REF_forces` round-trips **natively** via `AtomPositionManager.configure(total_force=...)`/`apm.forces` — no info-key workaround needed. `REF_stresses` has no such native slot (`AtomPositionManager` only has `total_force` for force-like data), so it genuinely needs one: serialised into info before storage (`a.atoms.metadata["_REF_stresses"] = np.asarray(stress).tolist()`) and restored on retrieval (`np.array(meta.pop("_REF_stresses"))`). This is handled transparently by `GlobalDatabase._prepare_for_storage` / `_atoms_from_container`.

`count_all_by_config_type_and_formula()` does a single O(N) scan over all containers and returns `{config_type: {formula: count}}`. Use it instead of calling `count_by_config_type_and_formula()` multiple times.

### Test suite

Tests live in `tests/` with subdirectories mirroring the source layout. New directories added:
- `tests/database_tests/` — GlobalDatabase dedup and round-trip tests
- `tests/initialize_tests/` — `compute_initialization_needs` delta logic
- `tests/remote_submission_tests/` — direct (non-mocked-away) tests of `submitters.py`'s four functions; mocks only `RemoteJobExecutor.run_and_wait`, letting each submitter's own job-config-construction logic run for real. `executor.py` itself is still tested in `tests/utils_tests/test_utilities.py`.

All tests are marked `@pytest.mark.unit` **on each individual test method** (run without any external services). Do not apply the mark only at the class level — pytest's mark inheritance is configuration-dependent and `pytest -m unit` may miss class-level-only marks. The suite tests real code paths — no "mock-testing" (asserting that a mock returns what you told it to return).

Key test patterns:
- `GlobalDatabase` tests use real sage_lib via `GlobalDatabase(str(tmp_path / "db"))` for genuine round-trip verification.
- `compute_initialization_needs` tests use a `MagicMock` DB that returns controlled `count_all_by_config_type_and_formula()` dicts.
- `mace` is a real dev dependency, installed in the test environment (`uv sync`) — tests import it directly rather than mocking `sys.modules`.
- `wfl` is not installed — never patch or import it in tests.
- `rank_committee` tests (`TestRankCommittee` in `tests/mlip_train_tests/test_mace_training.py`, plus the `"valid"`-preference/fallback cases in `test_checkpoint_evaluation.py`) build real `evaluation_metrics.json` files under `tmp_path` via `save_evaluation(prediction_metrics(...))` — no real models needed (a small placeholder model file whose bytes `save_evaluation` checksums). Cover ranking by each metric, `valid`-over-`test` preference, and every raise path (no evaluations, missing fit, changed checkpoint). The generic trainer path is tested backend-free with a tiny `EMTTrainer` (`tests/mlip_train_tests/test_base.py`, and end to end through the workflow in `test_active_learning_workflow.py`).
