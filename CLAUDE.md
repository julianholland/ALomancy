## Logging

All output goes through Python's `logging` module. No bare `print()` calls exist in `src/`.

```python
# Single configuration point — called in BaseActiveLearningWorkflow.__init__
from alomancy.utils.logging_config import setup_logging

setup_logging(verbose=1, log_file="results/my_run.log")
```

| `verbose` | Console | File (`results/alomancy.log`) |
|---|---|---|
| 0 (default) | WARNING+ only | DEBUG always |
| 1 | INFO (step progress) | DEBUG always |
| 2+ | DEBUG (per-job detail) | DEBUG always |

The file handler always writes DEBUG so every run produces a complete timestamped record. ExPyRe job stdout/stderr are captured at DEBUG level.

Each module declares `logger = logging.getLogger(__name__)` — no per-module setup needed. The `"expyre"` logger is also routed through the same handlers.

**Testing logs:** pytest's `caplog` does not intercept alomancy logs because `propagate=False` is set on the root alomancy logger. Attach a `logging.Handler` directly to `logging.getLogger("alomancy")` in tests that need to assert on log output (see `test_seed_logs_message` in `test_base_active_learning.py`).

## Architecture

ALomancy implements active learning (AL) workflows for training machine-learned interatomic potentials (MLIPs). The core loop is: **train MLIP committee → MD structure generation → uncertainty-based selection → DFT evaluation → extend training set → repeat**.

### Core layer (`src/alomancy/core/`)

`BaseActiveLearningWorkflow` (abstract) owns the AL loop in its `run()` method. It calls four abstract methods that concrete subclasses must implement:

- `initialize_training_set(base_name)` — produce initial `(train_xyzs, test_xyzs)` atom lists
- `train_mlip(base_name, job_dict)` → `pd.DataFrame` of evaluation metrics
- `generate_structures(base_name, job_dict, train_atoms_list)` → `list[Atoms]` of high-uncertainty candidates
- `high_accuracy_evaluation(base_name, job_dict, structures)` → `list[Atoms]` with DFT results

`ActiveLearningStandardMACE` (in `standard_active_learning.py`) is the production implementation: MACE committee for the MLIP, ASE MD for structure generation, Quantum Espresso (QE) for DFT.

All results land under `results/<base_name>/` with a fixed subdirectory layout. The workflow has **idempotency logic** throughout: each step checks for existing output files and skips remote submission if they exist, enabling restart after failures.

`run()` calls `self.pre_run_checks()` first, which calls `display_workflow_summary()` (logs a per-phase settings summary — flattened from each phase's job dict up to 2 levels deep, so it reflects whatever module/calculator is configured without hardcoding per-algorithm keys — plus a table of HPC profiles in use: GPU/partitions/node stats/job types/installed alomancy version) and then checks the installed version (`alomancy.version.__version_tuple__`) against the latest published PyPI release: warns if behind by a minor release, raises `RuntimeError` if behind by a major release. Skipped gracefully on network failure (never blocks an offline HPC run) and skipped outright under `ALOMANCY_TEST_MODE`/`ALOMANCY_MOCK_EXTERNAL` (never makes a real network call in tests).

### Configuration (`src/alomancy/configs/`)

`load_dictionaries(config_path)` reads a YAML file into a `jobs_dict` passed to the workflow constructor. Four top-level keys are required: `initialization`, `mlip_committee`, `structure_generation`, `high_accuracy_evaluation`. Each carries a `name`, `max_time`, and `hpc` value.

**HPC string resolution**: `hpc:` may be either a dict (full inline profile, backwards-compatible) or a string name (e.g. `hpc: 'raven_gpu'`). When it is a string, `load_dictionaries` looks it up in `~/.alomancy/hpc_config.yaml` (loaded by `global_config._load_global_hpc_config()`) and substitutes the full dict in-place. Raises `ValueError` if the named profile is not found — message directs the user to `alomancy add-hpc`.

`global_config.py` holds path constants (`ALOMANCY_HPC_CONFIG = ~/.alomancy/hpc_config.yaml`, `EXPYRE_CONFIG = ~/.expyre/config.json`) and `_load_global_hpc_config()`.

`RemoteInfo` and `get_remote_info()` convert a job sub-dict into an Expyre `RemoteInfo` object. The `sys_name` field maps to an Expyre system name (defined in the user's Expyre config, not in this repo).

### Remote execution (`src/alomancy/remote_submission/executor.py`)

**See `docs/remote_submission_architecture.md` for the full picture**: a from-source audit of every function in `remote_submission/` (submitters, executor, `RemoteInfo`) plus a strategy review, covering exactly what's tested vs. not, dead code/config fields, and case studies tracing several real production incidents (a permanently-lost committee model, silent local-disk exhaustion, a corrupted-then-diagnosed parity-plot dataset) back to specific gaps — most of which are now fixed and cross-referenced there. Read it before making non-trivial changes to this subsystem; the summary below covers only what every session needs to know up front.

`RemoteJobExecutor` wraps Expyre's `ExPyRe`. Call pattern: `submit_multiple_jobs → run_all_jobs_bounded → cleanup_jobs`; the convenience method `run_and_wait` does all three steps. `run_all_jobs_bounded` runs a `ThreadPoolExecutor(max_workers=remote_info.max_concurrent_jobs)`, one `.start()`+`.get_results()` task per job — jobs beyond the cap queue automatically and the pool starts the next one the instant a worker thread frees up (success or failure), rather than submitting everything up front and waiting for results strictly in submission order. **ExPyRe's job DB is not thread-safe by default**: `expyre.config.db` is a single module-level sqlite3 connection opened with `check_same_thread=True`, and every read/write funnels through one choke point (`JobsDB._execute`). `_ensure_expyre_db_thread_safe()` (called once per `run_all_jobs_bounded`) reopens that connection with `check_same_thread=False` and wraps `_execute` in a lock — locking only the brief DB transaction, not the callers' polling sleeps, so real concurrency of the waiting is preserved. Submitters that mix job kinds in one pool (e.g. `ase_remote_submitter`'s GO/SP split, see below) pass a per-job `"function"` override in each `job_configs[i]` dict, which `submit_multiple_jobs` honours in place of its shared `function` argument.

**Transient remote failures are resumed, not treated as permanent** (`_get_results_with_resume`, called from `_run_single_job`): a `get_results()` exception is resumed on the *same* job object, rather than abandoning it, whenever `job.status` is in `_RESUMABLE_JOB_STATUSES` — the ongoing statuses (`created`/`submitted`/`started`, expyre raised from transport, e.g. an rsync "No space left on device", before ever updating status for that poll) **plus** `'succeeded'` (expyre sets this *before* it copies output files back to `cwd`, so a local ENOSPC-class failure during that copy-out alone still has status `'succeeded'` and is just as safe to retry — remote status is already `'done'`, so re-entering `get_results()` goes straight back to re-attempting the copy). Transport exceptions get up to 5 retries with exponential backoff; `ExPyReTimeoutError` gets exactly 1 — tracked with **separate counters per exception type**, not one shared counter, so an interleaved sequence of both types can't exhaust the wrong budget. Once `job.status` reaches `'failed'`/`'died'` (expyre's only two genuinely terminal statuses, both set *before* it raises), the exception re-raises immediately — no retry. A definitively died job (`ExPyReJobDiedError`) gets one fresh resubmission (`job.start(force_rerun=True)`, after `_salvage_partial_output` runs on the dead job first — `force_rerun=True` only wipes the *remote* stage dir, reusing the same local one, so anything not salvaged before resubmitting risks being overwritten by the replacement's own synced output) only if `RemoteInfo.resubmit_killed_jobs=True` (default `False` — a killed job often needs different resources, not just an identical retry). `cleanup_jobs()` only calls `mark_processed()` on terminal-status jobs, never on one still ongoing after resume retries are exhausted — `'processed'` is excluded from expyre's own restart-reattachment logic, so marking a possibly-still-running job processed would permanently orphan it.

**PyTorch triton requirement**: Recent PyTorch versions ship native triton-backed GPU ops via `torch._native` (confirmed present in torch 2.13). Triton JIT-compiles CUDA extensions at runtime, which requires `python3-dev` (Python headers) on the compute node. HPC compute nodes typically do not have these headers. Fix: set `TRITON_CACHE_DIR` to a persistent path in the `mlip_committee` `pre_cmds` and pre-warm the cache once in an **interactive GPU job** (not the login node — the login node driver may be too old). `mace_wfl.py` logs a WARNING at import time if `torch._native` is detected and `TRITON_CACHE_DIR` is not set. Pre-warm command (run inside an interactive GPU job): `TRITON_CACHE_DIR=/fhi/home/jholl/.triton_cache python -m mace.cli.run_train --help`

**Remote deployment**: ExPyRe serializes functions **by reference** (module path + function name). The remote machine imports the module to resolve the function at run time. When changing the signature or body of any function submitted remotely (e.g. `mace_fit`), you must reinstall the updated package on the remote machine (`pip install -e .` there) before restarting, or jobs will import the old code and fail with a `TypeError` at the call site — typically hours after submission.

**Nested `srun` must not request its own `--mem`**: `_build_srun_command` (`utils/dft_utils.py`) launches the DFT/MLIP binary via `srun` from inside the job's own batch script, and requests `--mem=0` — Slurm's documented sentinel for "use all memory already granted to the job." Do not change this to an explicit sub-amount (e.g. `--mem={max_mem_per_node}`): on Slurm configs where the running batch script is accounted as the job's first step and credited with the job's *entire* memory allocation, a nested step's own explicit request competes with that reservation and fails immediately with `"Unable to create step ... Memory required by task is not available"` — regardless of how much memory the job was granted or how small the request is. The job-level memory ceiling belongs on the outer `#SBATCH --mem` line (see next paragraph), not on the inner `srun`.

**HPC wizard memory headers are per-partition**: `add_hpc_wizard()` (`cli/add_hpc.py`) collects `max_mem` per partition and bakes each partition's own `#SBATCH --mem=<N>M` line into that partition's `header` entry in `~/.expyre/config.json` (via `_with_partition_mem_headers`), not into the system-wide header. ExPyRe applies a partition's `header` list in addition to the system-wide header for any job that lands on it. A single blanket `--mem` shared across all of a system's partitions is wrong whenever those partitions have different node memory sizes — it under-requests on large-memory partitions or gets jobs rejected outright on small ones. `node_info.max_mem_per_node` in `~/.alomancy/hpc_config.yaml` is descriptive metadata only; it does not drive any `#SBATCH`/`srun` `--mem` value.

### Key conventions

- All file I/O uses `extxyz` format via ASE's `read`/`write`.
- Energy and force labels stored in `atoms.info["REF_energy"]` and `atoms.arrays["REF_forces"]`. **Never use bare `"energy"` as an info key** — ASE moves it to the calculator on extxyz read, losing it from `atoms.info`.
- Structures that need geometry optimisation carry `atoms.info["needs_relaxation"] = True`. **This flag is never cleared automatically** — it survives `atoms.copy()` (and `clean_structures`'s `structure.info.copy()`) through GlobalDatabase storage and back out again. If a `needs_relaxation=True` structure is later reused as an MD seed, every MD trajectory frame derived from it inherits the flag too. Any code path that generates structures which must never be relaxed (e.g. `generate_structures` in `standard_active_learning.py`) must explicitly set `needs_relaxation=False` on its output rather than relying on the key being absent.
- `config_type` in `atoms.info` tracks provenance (e.g. `"initialization"`, `"init_dimer"`, `"high_sd"`). Structures selected by the AL loop uncertainty criterion get `config_type="high_sd"` (set by `clean_structures` in `base_active_learning.run()`); the per-loop index is stored separately in `atoms.info["al_loop"]` via `extra_metadata`. Do not use `"al_loop_N"` as a config_type — the loop number is not embedded in the type string.
- The `seed` parameter (default `803`) is used everywhere randomness appears for reproducibility.
- `run_md` (`structure_generation/md/md_wfl.py`) takes `ensemble: "nvt" | "npt"` (default `"nvt"`) plus `pressure` (GPa, only used for `"npt"`) via `structure_generation.run_md_kwargs` in the config. `"nvt"` runs fixed-cell `ase.md.langevin.Langevin`; `"npt"` runs `ase.md.langevinbaoab.LangevinBAOAB` with a variable cell targeting `pressure`. An unrecognized `ensemble` string raises `ValueError` immediately rather than leaving the dynamics object unset. **`LangevinBAOAB`'s `externalstress` must never be passed as `None` for the NPT path** — ASE only activates its barostat (cell momentum steps, cell Langevin thermostat) when `externalstress is not None`; passing `None` silently degrades "npt" to fixed-cell dynamics indistinguishable from `"nvt"` but running the more expensive BAOAB integrator for no benefit. `run_md` derives it as `-pressure * ase.units.GPa` (ASE's stress-is-negative-of-pressure convention), so even the default `pressure=0.0` yields `externalstress=0.0` — not `None` — keeping the barostat live and targeting zero external pressure.
- `select_initial_structures` (`structure_generation/select_initial_structures.py`) reuses structures with replacement when `max_number_of_concurrent_jobs` exceeds the number of structures passing the `chem_formula_list`/`selectable_configs`/`atom_number_range` filters — it no longer raises. Each of the `max_number_of_concurrent_jobs` returned atoms gets a distinct `atoms.info["md_seed"] = seed + i`, which `run_md` (`structure_generation/md/md_wfl.py`) reads to seed Langevin's `rng`; without this, two concurrent MD jobs started from the same duplicated structure would (depending on process-level RNG state) risk producing identical or under-diverged trajectories. A `ValueError` is only raised when the filtered pool is empty (nothing to reuse from at all).
- `find_high_sd_structures` (`structure_generation/find_high_sd_structures.py`) takes whatever candidates are available forward instead of crashing when fewer survive upstream filtering than `desired_number_of_structures` requests — analogous to `select_initial_structures` above, but on the output side of MD/uncertainty selection rather than the seed-selection input side. If `len(structure_list) < desired_number_of_structures`, it logs a WARNING and selects `min(desired_number_of_structures, len(structure_list))` structures by force std dev instead of asserting. A `ValueError` (not `AssertionError`) is raised only when `structure_list` is completely empty or `desired_number_of_structures <= 0` — both former `assert` statements, converted per this codebase's guard-with-`ValueError` convention (see above) even though this function currently only runs in the local driver process, not inside a remotely-submitted function.
- `verbose` is an int: `0` = silent, `>0` = progress prints.
- The global DB lives at `results/global_database/` (configurable via `db_path` in `BaseActiveLearningWorkflow.__init__`). Only DFT-evaluated structures (with `REF_energy`/`REF_forces`) are stored in it.
- Every structure in `GlobalDatabase` carries `atoms.info["global_db_id"]`: a zero-based integer index assigned at insertion time, stable across sessions. Call `db.assign_global_db_ids()` to backfill existing DBs.
- `BaseActiveLearningWorkflow` accepts `remove_redundancy=True` and `high_force_threshold=100.0` — these run after initialization and after each AL loop to prune similar structures and exclude unphysical forces from the DB before the next training round.
- `skip_initialization=True` on `BaseActiveLearningWorkflow`: when no AL loops have completed, loads train/test from the DB and starts at `start_loop` without calling `initialize_training_set`. Useful when the DB is pre-populated.
- `generate_structures` uses `select_best_committee_model` (lowest test-set `mae_f` from `fit_*/results/*_test.txt`) as the MD base model; all other fits form the uncertainty comparison committee. `fits_to_use` excludes the best fit index to avoid double-counting in the std-dev computation.
- Energy MAE reported as `mae_e_per_atom` (eV/atom) everywhere — `get_mace_eval_info`, `plotting.py`, and `mlip_plots.py` all use this key. Never use `mae_e` (total energy per structure) in plots; it has similar magnitude to `mae_f` and causes visual confusion.
- **No plotting path may be interactive**: `alomancy/__init__.py` calls `matplotlib.use("Agg")` before any submodule can import `matplotlib.pyplot`, since `RemoteJobExecutor.run_all_jobs_bounded` polls jobs from a `ThreadPoolExecutor` and any `Figure` created under an interactive backend (matplotlib's default whenever `DISPLAY` is set, e.g. `TkAgg`) that gets garbage-collected on a worker thread crashes the whole process with SIGABRT (Tkinter finalizers calling back into Tk from the wrong thread). Every plotting function creates a figure, saves it, and closes it (`plt.savefig` + `plt.close(fig)`) — never `plt.show()`. `analysis/plotting.py`'s `Plot` class has no `show()` method for the same reason; `Plot.save()` closes its own figure after writing.
- **`_ensure_expyre_db_thread_safe`'s lock must cover the fetch, not just the query**: `_locked_execute` (`remote_submission/executor.py`) patches `JobsDB._execute`, expyre's sole low-level sqlite access point. `self.db.execute(cmd)` returns a live, unfetched `sqlite3.Cursor` — every caller in expyre's `jobsdb.py` only consumes it *afterward* (`list(self._execute(...))`, `for row in self._execute(...)`). Releasing the lock right after `execute()` returns (rather than after the rows are actually fetched) leaves a window where a second thread's own `execute()` call on the same shared connection (`check_same_thread=False` disables sqlite3's same-thread assertion, not genuine concurrent-cursor safety) can corrupt the first thread's still-pending read, silently yielding zero rows for a row that genuinely exists — this was the real cause of a production `list(config.db.jobs(id=...))[0])` `IndexError` (`expyre/func.py`) from a *single* process with many concurrent job-monitoring threads (e.g. `structure_generation` polling ~20 MD jobs at once), not cross-process contention as originally suspected. `_locked_execute` now materializes the cursor into a `list` *inside* the lock before releasing it. `_get_ssh_call_lock`/`acquire_local_expyre_lock` (`threading.Lock`/`fcntl.flock` respectively) remain thread- and process-scoped defenses against a *different* class of contention (concurrent ssh sessions on one host; two alomancy processes sharing one `local_stage_dir`) — neither was the cause of this specific bug. `_run_single_job`'s failure handler logs the full traceback at DEBUG level (`results/alomancy.log`) for any future `IndexError`/similar failure, which is what made this one identifiable from a production log instead of needing source-level archaeology.
- **Every AL run gets its own isolated ExPyRe job-tracking state by default**: `alomancy/__init__.py`'s `_ensure_local_expyre_root` runs at package-import time (before anything can import `expyre.config` and trigger its own one-time resolution) and copies ALomancy's canonical HPC systems config — `configs/global_config.py`'s `EXPYRE_CONFIG`, i.e. `~/.alomancy/expyre_config.json`, written by `alomancy add-hpc` — into a fresh `<rundir>/.expyre/config.json`, unless that directory already has a `.expyre`/`_expyre` (idempotent) or `EXPYRE_ROOT` is set explicitly (bypasses expyre's directory walk entirely, so a run-local `.expyre` would never be consulted). expyre's own config resolution walks from cwd up to `$HOME`, merging every `.expyre`/`_expyre` it finds and using the *deepest* one as `local_stage_dir` — the directory holding both `jobs.db` and every job's stage directory (`ExPyRe.__init__`'s `tempfile.mkdtemp(dir=config.local_stage_dir)`) — so a run-local copy becomes the one actually used, isolating this run's job state from every other alomancy run on the same machine or shared home directory. It's a one-time snapshot, not a live reference: editing `EXPYRE_CONFIG` later doesn't retroactively affect a run whose `.expyre/` already exists. `write_expyre_config` (`cli/add_hpc.py`) migrates one-time from `LEGACY_EXPYRE_CONFIG` (`~/.expyre/config.json`, the pre-isolation location) the first time it writes `EXPYRE_CONFIG` and finds it missing, so systems configured before this existed aren't lost — raises `ValueError` rather than silently dropping data if the legacy file it's migrating from turns out to be corrupt, matching how a corrupt canonical file is already handled. `alomancy nuke`'s default target (`cli/nuke.py`'s `resolve_default_expyre_dir`) resolves the same way, falling back to `~/.expyre` only if no local config has been resolved yet — so nuking from inside a project directory only clears that project's own job state. `resolve_hpc_host` (`utils/remote_ssh.py`, used by the workflow-startup remote-version check and `alomancy upgrade-hpc`) tries `EXPYRE_CONFIG` then falls back to `LEGACY_EXPYRE_CONFIG` too — every reader of ExPyRe's systems config must fall back the same way, or an installation that hasn't re-run `alomancy add-hpc` since upgrading silently loses that reader's ability to find its HPC systems.
- **`acquire_local_expyre_lock`** (`remote_submission/executor.py`), called at the start of `pre_run_checks()` before any remote submission: takes an exclusive, non-blocking `fcntl.flock` on `expyre.config.local_stage_dir`, raising `RuntimeError` immediately if another alomancy process already holds it (a no-op if this process already holds it, or if `local_stage_dir` hasn't resolved yet). POSIX-only, matching this codebase's Linux/HPC-only environment. Unlike a hand-rolled PID-file check, the OS releases an `flock` automatically the instant the holding process's file descriptor closes — including on a crash or `kill -9` — so a dead process never leaves a stale lock blocking a legitimate restart. The lock file records `pid`/`host`/`started` for diagnostics if a conflict is hit. The check-and-set of its module-global lock handle is itself guarded by `_expyre_root_lock_guard` (double-checked locking, matching `_get_ssh_call_lock`'s pattern) — `flock` is scoped per *open file description*, not per-process, so two threads racing this function in the same process could otherwise each open a fresh file description and have the second one fail against the first's already-held lock, incorrectly reporting itself as a conflicting process.
- **`RemoteInfo.lock_timeout` defaults to `None` (wait indefinitely for the per-host ssh-call lock, `_get_ssh_call_lock`), not derived from the job's `max_time`.** A prior version set it from `max_time` so a `RemoteJobExecutor` worker thread queued behind another one stuck on an interactive ssh password/OTP prompt would give up and fail loudly after that duration rather than just waiting — but the thread genuinely *holding* the lock and blocked on that prompt was never bounded either way (no timeout exists anywhere on the underlying `subprocess.Popen(...).communicate()` call inside `expyre`), so the revert only ever turned "everything queued behind it waits quietly, exactly as long as it takes someone to type the password" into "everything else fails loudly around the one thing that's still just waiting." Reverted to the pre-existing behavior. `pre_run_checks()`'s `ensure_ssh_connectivity` (`utils/remote_ssh.py`) is the actual fix for the underlying problem this was trying to guard against: it runs a bare `ssh <host> true` (no `timeout=`, no `capture_output=`, so a password/OTP prompt prints to and reads from the real terminal) once per distinct HPC host configured in the run, before any remote submission begins — while whoever launched the run is presumably still at the terminal to answer it, rather than however many hours later a background worker thread first happens to touch that host unattended. If the host's ssh config uses connection multiplexing (`ControlMaster`/`ControlPersist`), authenticating here establishes the shared control connection once so every later call from `RemoteJobExecutor` reuses it silently. Never raises — an unreachable host is logged as a warning and left for the real remote submission to fail loudly on later.
- Initialization config uses individual counts (`num_dimers_per_combo`, `num_trimers_per_combo`, `num_amorphous`, `num_stretch_compress_per_mp`) rather than the old `d_t_s_a_ratio` + `target_non_mp_structures_to_add`.
- `creation_kwargs.max_atom_number` and `creation_kwargs.amorphous_atom_number` are separate knobs (both default to `20`): `max_atom_number` caps atom count for Materials Project fetches (`atoms_list_from_mp`'s `max_num_atoms`), `amorphous_atom_number` sets the target atom count per generated amorphous cell (`create_amorphous_atoms_list`'s `atom_number`). They used to be the same value (`max_atom_number` drove both); changing one no longer affects the other.
- `creation_kwargs.mp_max_energy_above_hull` (default `0.1` eV) sets the energy-above-hull cutoff for Materials Project fetches (`atoms_list_from_mp`'s `max_energy_above_hull`), previously hardcoded. Only affects MP structures, not amorphous/dimer/trimer generation.
- `IsolatedAtom` and `init_MP` config_types are deduplicated by `(config_type, formula)` in `GlobalDatabase.add_structures()`; other config_types (dimers, trimers, amorphous, AL loop structures) are always added without exact dedup.
- In `initialize_training_set`, the DB is checked **first** (`compute_initialization_needs` against current DB state). `extra_datasets` are seeded only if the DB is still missing some initialization targets, then needs are re-checked before any structure generation. An already-populated DB is always honoured before consulting extra datasets.
- `initialize_training_set` has two paths: (1) fast path — if `initial_train_file_path` and `initial_test_file_path` exist on disk, load them directly; (2) DB path — call `compute_initialization_needs`, generate only missing structures, run DFT, build train/test from `db.get_all_as_atoms()`.
- `jobs_dict["high_accuracy_evaluation"]["name"]` must equal `"high_accuracy_evaluation"`. `ase_remote_submitter` always writes output to the hardcoded path `results/<base>/high_accuracy_evaluation/batch_N/`; the result-collection glob in `standard_active_learning.high_accuracy_evaluation` uses `output_name` (i.e. the `name` field) as the subdirectory. If they diverge the glob finds nothing, an empty sentinel is written, and the phase is permanently marked done with zero structures.
- Guard user config errors in functions that run remotely with `if`/`raise ValueError(...)`, not `assert`. Python's `-O` flag (common in HPC module environments) strips all asserts silently, deferring config failures to the remote job hours after submission.
- **VASP pseudopotentials**: ASE's `Vasp` calculator reads POTCAR locations only from the `VASP_PP_PATH` environment variable — there is no constructor kwarg for it. `create_vasp_calc_object` (`high_accuracy_evaluation/dft/run_vasp.py`) sets `os.environ["VASP_PP_PATH"] = hpc["pp_path"]` before building the calculator whenever `pp_path` is present in the HPC profile. `pp_path` must point at the directory *containing* `potpaw_PBE`/`potpaw_LDA`. Elements without a `pseudo_dict` override fall back to the default (unsuffixed) POTCAR under that path; if the library doesn't carry a given element, VASP fails with `No pseudopotential for <element>!`.
- **VASP requires full periodicity**: ASE's `Vasp` calculator rejects any `pbc` other than `[True, True, True]` — VASP has no non-periodic mode. Non-periodic structures (isolated atoms, dimers, trimers from initialization) are padded with vacuum and forced to `pbc=True` by `_ensure_fully_periodic` inside `create_vasp_calc_object` before the calculator is built. QE's `Espresso` calculator handles non-periodic cells natively and needs no equivalent step.
- GO (geometry-optimisation) and SP (single-point) structures in `high_accuracy_evaluation` share a single batch dir and a single `ase_remote_submitter` call (`batch_num = current_batches`, the count of existing `batch_*` dirs — still needed for restart-safety, to avoid colliding with a prior partial run). They're no longer split into separate batches; `per_structure_function` picks `run_go` or `run_sp` per structure from its own `needs_relaxation` flag, and both kinds roll through the same `RemoteJobExecutor` pool, distinguished only by a `go_`/`sp_`-prefixed job name. If any structure in the batch needs relaxation, the shared `RemoteInfo`'s walltime is built from `max_go_time` (the GO ceiling) rather than the plain `max_time`, since SP jobs finishing early under a longer walltime is harmless but a GO job running under an SP-sized one is not.
- `max_concurrent_jobs` (HPC profile, `~/.alomancy/hpc_config.yaml`, default `20`, set via the `alomancy add-hpc` wizard) caps how many jobs a `RemoteJobExecutor` keeps started at once — see `RemoteInfo`/`get_remote_info` (`configs/remote_info.py`). The deprecated job-dict-level `max_batch_size` key is used as a fallback only when the HPC profile doesn't define `max_concurrent_jobs`, with a logged warning either way; it will be removed in 1.0.0 (see `docs/deprecations.md`). This is unrelated to `structure_generation`'s `max_number_of_concurrent_jobs` (`select_initial_structures.py`), which controls how many seed structures are selected for MD, not scheduler concurrency.
- **MACE prediction files**: after `mace_fit` finishes training on the remote GPU, `_save_mace_eval_predictions` writes `train_pred.xyz` and `test_pred.xyz` in `results/<base>/<name>/fit_<i>/`. These files carry `mace_energy` (float, eV) and `mace_forces` (array, eV/Å) keys alongside the standard DFT keys. `store_mlip_predictions` (in `standard_active_learning.py`) reads these files locally and stores predictions in the GlobalDB using keys `mace_energy_loop_{N}_fit_{i}` / `mace_forces_loop_{N}_fit_{i}`. `plot_dft_vs_model` reads from DB first, then falls back to these files, then skips with a blank subplot — **never runs local MACECalculator inference**. Loops trained before v0.4.2 will not have the eval files; the sentinel (`mace_predictions.done`) is written and skipped gracefully. **`_save_mace_eval_predictions` evaluates the uncompiled `{name}_stagetwo.model`, not the TorchScript-compiled `{name}_stagetwo_compiled.model`**: the compiled model's force evaluation (`torch.autograd.grad` through the TorchScript interpreter) can raise `RuntimeError: ... Global alloc not supported yet` for every multi-atom structure on some GPU/CUDA/PyTorch combinations, with only the trivial single-atom case succeeding — silently degrading every parity plot to one point. Eager-mode (uncompiled) execution bypasses the TorchScript interpreter's op dispatch entirely; this function runs a few thousand single-point evaluations once per fit per loop, not a performance-critical path, so eager-mode correctness is worth more than compiled-inference speed here. Its existence gate checks the uncompiled model too, not the compiled one — MACE (`mace/cli/run_train.py`) writes the uncompiled model unconditionally but wraps the compiled variant's `jit.compile()`/`torch.jit.save()` in a bare `except Exception: pass`, so gating on the compiled file would skip valid predictions whenever that silent compile step happens to fail.
- **MACE checkpoint cleanup is two-part, remote and local, and both are required**: `_cleanup_committee_checkpoints` (`mlip/mace_wfl.py`, runs inside `mace_fit` on the remote node) deletes a fit's `checkpoints/` directory once its compiled model exists — but this alone does *not* bound local disk usage, since ExPyRe's periodic mid-training sync (`get_remotes()`, called on every `get_results()` poll) pulls the entire remote stage directory back with `delete=False` (additive-only): every distinct, epoch-numbered checkpoint filename MACE's own rotation ever wrote and then deleted remotely still accumulates locally, one snapshot per sync poll, across a multi-hour training run (observed: 5–7GB per fit despite the remote cleanup succeeding). `cleanup_local_committee_checkpoints` (same file, called from `train_mlip` once a batch of committee jobs finishes) separately removes each fit's *local* `checkpoints/` directory, gated the same way (only once that fit's compiled model exists locally).
- **Formation-energy parity plots**: `plot_dft_vs_model` plots *formation energy per atom* (`(E - sum(E0[symbol] for symbol in structure)) / n_atoms`), not raw per-atom energy, whenever a `GlobalDatabase` is available and has `IsolatedAtom` structures — `GlobalDatabase.get_isolated_atom_energies()` builds the `{symbol: REF_energy}` dict once per loop from those, and it is threaded into both `get_mace_predictions(..., e0=...)` (DB tier) and `_parse_eval_xyz(..., e0=...)` (xyz-fallback tier). The same E0 shift is subtracted from both DFT and model energy for a given structure, so it cancels exactly in the reported `mae_e_per_atom`/MAE annotation — it only changes the *shape/spread* of the parity scatter, not the training-curve MAE plots (`mae_al_loop_plot`, `plot_training_curves`), which read `mae_e_per_atom` straight from MACE's own eval output and are untouched by this. Falls back silently to raw per-atom energy (logging one WARNING) when no `GlobalDatabase`/no `IsolatedAtom` entries are available, or when a structure contains an element missing from the E0 dict — this preserves old behavior for pre-formation-energy runs and never mixes formation- and raw-energy points within one figure. `alomancy replot` opens the `GlobalDatabase` at `results_dir/global_database` (matching `GlobalDatabase.__init__`'s default `db_path`) if it exists, so replotted parity plots match the live AL loop's; older results directories without a `global_database/` fall back gracefully.
- **Per-loop plots live in their own subdirectory, `results/current_plots/<base_name>/`** (e.g. `results/current_plots/al_loop_4/`), not flat in `results/current_plots/` alongside every other loop's files. `plot_training_bond_distances`, `mae_al_loop_plot`, `plot_training_curves`, and `plot_dft_vs_model` are each called with that loop's own subdirectory as their `plots_dir`/`directory` argument — the reorg is implemented entirely at the call site (`base_active_learning.py`'s AL loop constructs `loop_plots_dir = plots_dir / base_name` once per iteration; `alomancy.cli.replot` mirrors the same layout, and for its once-per-run cross-loop `mae_al_loop_plot` call — which shows the fullest cumulative history — writes into the *last* plotted loop's subdirectory to match what the live run's final loop would have produced), not inside any of the plotting functions themselves, which are unaware of the directory scheme and still take a `plots_dir: Path` and write into it directly. Filenames are unchanged (still `_al_loop_N`-suffixed, e.g. `training_mae_al_loop_4.png`) — only the directory changed. `plot_training_curves` also writes each fit's per-epoch `loss`/`mae_e_per_atom`/`mae_f` to a `metrics/` subdirectory *under that same per-loop directory* (`results/current_plots/<base_name>/metrics/<base_name>_fit_<i>_training_metrics.csv`), alongside the PNGs rendered from the same DataFrame — the raw numbers behind a plot no longer require re-parsing `*_train.txt`. Run-level aggregate plots — currently only the combined timing plot below — are the one exception: they summarize across all loops, not just one, and stay flat at the top of `results/current_plots/`.
- **`timing_plots` (`analysis/timing_plots.py`) writes a single combined figure, `results/current_plots/timing_combined.png`** — a stacked bar chart of wall-clock time per phase per AL loop (queue/running sub-segments, same data `timing_phases.png` used to show) overlaid with a line on a secondary y-axis (`ax.twinx()`) giving the number of training structures per loop (the information the old, now-removed `timing_total.png` carried as text labels on its own separate bar chart). The legend is at `upper left` and combines both axes' handles in one `ax.legend(h1 + h2, l1 + l2, ...)` call — a bare `ax.legend()` after `twinx()` silently drops the second axis's line from the legend. The figure width is a fixed `figsize=(10, 6)` regardless of the number of loops, unlike the old two-plot version's `max(4, len(loops) * 1.2 + 1)` sizing, which grew unbounded over a long run; bars get more cramped with many loops on a fixed-width figure, an accepted, explicitly requested tradeoff. Same public signature (`timing_plots(log_file, directory)`) as before, called once per loop from `base_active_learning.py` and once from `alomancy.cli.replot` — this is a run-level aggregate, so it is the one plot that stays flat in `results/current_plots/` rather than moving into a per-loop subdirectory.
- `initialize_training_set`'s `test_to_train_ratio` applies only within the `test_config_types` pool (e.g. `init_amorphous`, `init_MP`), never against the whole DB — dimers/trimers/stretch_compress/`IsolatedAtom` never count toward it. Computing the quota against the full DB could route 100% of a small `test_config_types` pool into test, and since `update_splits_post_hoc` never re-tags an already-tagged DB container, that config_type would be permanently starved out of `train_atoms_list` on every subsequent loop. A backstop still reserves one structure per config_type against an unlucky shuffle leaving one out entirely.
- `train_mlip`'s committee backfill retrains **every** missing `fit_idx` whenever any are missing (not just enough to reach 3), via `committee_remote_submitter(..., fit_indices=[...])`, never `range(size_of_committee)` from 0 — the latter would silently overwrite already-successful low-index fits instead of the ones that actually failed, since `mace_fit` derives its output directory purely from `fit_idx`. 3 remains the floor for a usable committee std-dev, but only as the post-retry hard-failure check: `train_mlip` raises unless at least 3 models exist after retrying, rather than proceeding with an unusable committee. (Previously the retry only fired *and* only retrained enough fits to reach 3, so a fit lost after 3 others already succeeded was never retried again for the rest of that AL loop — root cause of a production crash, see `select_best_committee_model` below and `docs/remote_submission_architecture.md` §6.2.)
- `select_best_committee_model` (`mlip/get_mace_eval_info.py`) only considers fits whose `{name}_stagetwo.model` file actually exists on disk, in both its metric-based scoring loop and its no-readable-test-metrics fallback (which picks the lowest-indexed fit *with* a model, not unconditionally `fit_0`) — raises `ValueError` only if literally none of the committee's fits have a model. Previously the fallback returned `fit_0`'s path with no existence check, which crashed `generate_structures` (staging a nonexistent model as an MD job input) the one time `fit_0` itself was the fit that failed.
- `RemoteJobExecutor._run_single_job` resumes a job on transient remote-communication failures instead of abandoning it — see the "Remote execution" section above and `docs/remote_submission_architecture.md` §3.3 for the full mechanism.
- `generate_structures`'s reload of an existing `structure_generation_input_structures.xyz` passes `index=":"` to `ase.io.read` — a bare `read()` call defaults to returning only the *last* frame — and validates the reloaded count against `structure_selection_kwargs.max_number_of_concurrent_jobs`, regenerating via `select_initial_structures` if it's short. Guards against a partially-written file (e.g. an HPC filesystem filling up mid-write) being silently trusted and starving `find_high_sd_structures` of candidates several steps downstream.
- **No structure with a pairwise atomic distance below 0.5 Å is ever submitted to DFT**: `filter_structures_by_min_bond_distance` (`utils/clean_structures.py`) is called both in `generate_structures` (before the MACE committee evaluation, not just before DFT — no point scoring an unphysical structure's uncertainty either) and again in `high_accuracy_evaluation` itself (a final safety net that also covers the initialization-bootstrap call site, which has no upstream filter of its own). `get_all_distances(mic=True)` is safe to call unconditionally across every `config_type` (periodic or not); single-atom structures always pass through.
- **Surviving structures are wrapped into their periodic cell immediately before DFT submission**: `wrap_structures_into_cell` (`utils/clean_structures.py`) is called in `high_accuracy_evaluation` right after `filter_structures_by_min_bond_distance` — only structures that already passed that filter get wrapped, since there's no point fixing an unphysical structure's cell positions. Guards against MD trajectories leaving atoms drifted outside the cell (a normal MD artifact, unrelated to the short-bond-distance case the filter above handles); QE/VASP generally expect coordinates within the reference cell. Calls `Atoms.wrap()` unconditionally with no `pbc`-based guard — confirmed empirically against ASE 3.28 that it mutates in place (returns `None`), preserves `atoms.info`/`atoms.arrays`/any attached `atoms.calc` exactly, and is a safe no-op on non-periodic structures (positions on non-periodic axes, or on a `pbc=False` structure with no cell at all, are left unchanged).

### sage_lib / GlobalDatabase internals

`sage_lib.Partition` (hybrid HDF5+SQLite) only persists `atoms.info`, **not** `atoms.arrays`. `REF_forces` must be serialised into info before storage (`a.info["_REF_forces"] = forces.tolist()`) and restored on retrieval (`np.array(meta.pop("_REF_forces"))`). This is handled transparently by `GlobalDatabase._prepare_for_storage` / `_atoms_from_container`.

`count_all_by_config_type_and_formula()` does a single O(N) scan over all containers and returns `{config_type: {formula: count}}`. Use it instead of calling `count_by_config_type_and_formula()` multiple times.

### Test suite

Tests live in `tests/` with subdirectories mirroring the source layout. New directories added:
- `tests/database_tests/` — GlobalDatabase dedup and round-trip tests
- `tests/initialize_tests/` — `compute_initialization_needs` delta logic
- `tests/remote_submission_tests/` — direct (non-mocked-away) tests of `submitters.py`'s four functions; mocks only `RemoteJobExecutor.run_and_wait`, letting each submitter's own job-config-construction logic run for real. `executor.py` itself is still tested in `tests/utils_tests/test_utilities.py`.

All tests are marked `@pytest.mark.unit` **on each individual test method** (run without any external services). Do not apply the mark only at the class level — pytest's mark inheritance is configuration-dependent and `pytest -m unit` may miss class-level-only marks. The suite tests real code paths — no "mock-testing" (asserting that a mock returns what you told it to return).

Key test patterns:
- `GlobalDatabase` tests use real sage_lib via `GlobalDatabase(str(tmp_path / "db"))` for genuine round-trip verification.
- `compute_initialization_needs` tests use a `MagicMock` DB that returns controlled `count_all_by_config_type_and_formula()` dicts.
- `mace` is patched at the top of `test_standard_active_learning.py` via `sys.modules.setdefault(...)` before the module is imported (avoids GPU dependency at collection time).
- `wfl` is not installed — never patch or import it in tests.
- `select_best_committee_model` tests (`TestSelectBestCommitteeModel` in `tests/mlip_train_tests/test_mace_training.py`) write fake `*_test.txt` files under `tmp_path` and use `monkeypatch.chdir` — no real MACE models needed, but each fit expected to be considered **must have an empty `{name}_stagetwo.model` file touched** (via the `_touch_model` helper), since the function now filters to fits with an existing model before scoring. Cover both JSON-lines and Python list-of-tuples formats.
- `_write_train_txt` in `TestGetMaceEvalInfo` writes `mae_e_per_atom` (not `mae_e`) to match what `get_mace_eval_info` filters for.
